# MCP 一致性工程：版本、證據與維運

> 一台伺服器不會因為它的順風路徑在某個 SDK 上跑通了就算合規。一致性活在線路上、活在版本邊界上、活在中介之間，也活在回滾當下。

**類型：** 實作
**程式語言：** Python
**先修單元：** 階段 13 · 09（傳輸）、階段 13 · 17（閘道）、階段 13 · 30（登錄庫准入）
**時間：** 約 100 分鐘

## 學習目標

- 把 MCP 的規範性規則變成黃金與負向的線路逐字紀錄。
- 讓嚴格的 `2026-07-28` 行為，跟有界的舊版退路分開。
- 分辨可加的未知欄位，跟一個無效的未知 `resultType`。
- 把原始的 JSON-RPC 證據，跟 SDK 正規化後的視圖做比較。
- 跨過一個真實的代理邊界，證明標頭與本體的完整性。
- 用遮蔽後的逐字紀錄、健康狀態與回滾證據替發布把關。

## 問題所在

你的客戶端透過一個 SDK 呼叫 `tools/list`，拿到了工具。整合測試通過。

那個結果留下了幾個重要問題沒有回答：

- 請求有沒有帶著現代的逐請求協定中繼資料？
- `MCP-Protocol-Version`、`Mcp-Method` 與 `Mcp-Name` 有沒有跟 JSON-RPC 本體一致？
- 回應在線路上有沒有一個有效的 `resultType`，還是 SDK 自己合成了一個？
- 客戶端會不會保住一個未來才加上的欄位？
- 一個已辨識的現代錯誤，會不會不小心觸發舊版握手？
- 代理有沒有保住源站的狀態與 JSON-RPC 錯誤？
- 通知的序列化器有沒有送出一個被禁止的回應？
- 維運能不能在不存密鑰的前提下，證明某次發布為什麼被推上去或被回滾？

一致性是一組看得見的不變條件。做一個框架，在生產流量被迫發現它們之前，先把那些不變條件擷取下來。

```figure
mcp-conformance-operations
```

## 從版本紀元開始

MCP `2026-07-28` 用的是自我完備的逐請求中繼資料。一個現代請求會帶著 `params._meta.io.modelcontextprotocol/protocolVersion` 與 `params._meta.io.modelcontextprotocol/clientCapabilities`。那些具命名空間的鍵一字都不能差；光寫 `protocolVersion` 或 `clientCapabilities` 這種別名就是格式不對。當 HTTP 邊界上出現鏡像的路由標頭時，它們的值必須跟 JSON-RPC 本體一致。現代的成功結果會帶 `resultType`。

到 `2025-11-25` 為止的版本用的是較早的初始化紀元。一份沒有 `resultType` 的舊版結果，只有在客戶端已經選定那個較早的紀元之後，才會被解讀成 complete。

不要做一個同時接受兩種形狀的寬鬆驗證器。用兩條分支：

| 分支 | 進入的證據 | 缺少 `resultType` | 初始化 |
|---|---|---|---|
| 現代 | 成功的 `server/discover`，或一個已辨識的現代回應 | 無效 | 不是預設路徑 |
| 舊版 | 設定好的允許清單，加上在一次不確定的現代探測之後拿到的有效舊版 `initialize` 結果 | 被解讀成 complete | 那個紀元要求要有 |

這種分離能防止一個格式不對的現代對端，反而因此得到比較弱的驗證。

### 嚴格模式

嚴格模式要求現代行為的證明。一次成功的 `server/discover` 證明了現代分支。一個已辨識的現代 JSON-RPC 錯誤也證明得了。把請求修好，或停下來。絕不要因為伺服器回了 `-32020`、`-32021` 或 `-32022` 就降級。

### 退路模式

退路模式會做一次有界的現代探測。逾時、空回覆、連線關閉，或無法辨識的回應，都算不確定。它們證明不了那個對端是舊版。只有被明確設定或列入相容性允許清單的端點，之後才可以收到一次有界的舊版探測；而且只有在客戶端驗證過那次探測的 `initialize` 結果與協商出的舊版修訂版之後，才會選定舊版分支。

退路不是「出任何錯就試舊版」。一個已辨識的現代錯誤帶著有用的修正資訊。在它之後降級，會把標頭不一致、缺少能力宣告，或版本不支援這些問題藏起來。

這能防止攻擊者、停機或過濾型代理，靠著把現代回應丟掉來強迫降級。把端點政策、那次不確定的現代觀察、確切的正面舊版證據，以及選定的紀元一起記下來。

在每一份逐字紀錄旁邊都記下選定的紀元。少了那個事實，同一個缺漏欄位在某次測試裡看起來可接受，在另一次卻是無效的。

## 建一組逐字紀錄語料

一份逐字紀錄素材記的是有什麼跨過了那道邊界，不只是那次 SDK 呼叫：

```json
{
  "name": "golden-modern-list",
  "era": "modern",
  "headers": {
    "MCP-Protocol-Version": "2026-07-28",
    "Mcp-Method": "tools/list"
  },
  "request": {
    "jsonrpc": "2.0",
    "id": 1,
    "method": "tools/list",
    "params": {
      "_meta": {
        "io.modelcontextprotocol/protocolVersion": "2026-07-28",
        "io.modelcontextprotocol/clientCapabilities": {}
      }
    }
  },
  "responseStatus": 200,
  "responseBody": {
    "jsonrpc": "2.0",
    "id": 1,
    "result": {
      "resultType": "complete",
      "tools": []
    }
  }
}
```

保留兩類素材。

### 黃金逐字紀錄

黃金逐字紀錄證明的是被接受的行為：

- 中繼資料與標頭都相符的現代發現或方法請求
- 帶著必要欄位的 complete 結果
- 當那個方法可以要求更多輸入時的 `input_required` 結果
- 只有在對應能力被公告之後才出現的擴充結果
- 沒有 `resultType` 的舊版結果，但只在選定的舊版紀元裡
- 處理通知，而且沒有任何 JSON-RPC 回應

一份黃金逐字紀錄要精準，不必龐大。讓易變的 ID 與時間戳記維持決定性，或在比較之前先把它們正規化。

### 負向逐字紀錄

負向逐字紀錄證明的是拒絕行為：

- 標頭與本體不一致
- 缺少逐請求的能力
- 比對出來的協定版本不被支援
- 缺少現代的 `resultType`
- 未知或未被公告的 `resultType`
- 回應的 `jsonrpc` 不是 `2.0`，或 ID 的值或 JSON 型別不同
- 一個同時含有 `result` 與 `error`、或兩者都沒有的回應
- 一個沒有整數 `code` 與字串 `message` 的錯誤
- 一個被對映到錯誤 HTTP 狀態的已知協定錯誤
- 替一則通知送出的回應
- 格式不對的 JSON-RPC 信封
- 代理把協定錯誤塌掉

對每一個負向案例，都要斷言拒絕的邊界與穩定的錯誤碼。「這個呼叫失敗了」太弱。一個代理產生的 500 與一個源站的 `-32020`，看起來都像失敗，但對維運講的是完全不同的故事。

那份標頭不一致的素材，必須含有伺服器實際回的 HTTP 400 JSON-RPC 回應，帶著相符的請求 ID 與錯誤碼 `-32020`。只要本地驗證器觀察到 `HeaderMismatch`，就自動強制這一點；不要把回應驗證做成一個可選的素材旗標。一個 HTTP 500、而且沒有本體的案例，即使本地拒絕碼是對的也算失敗。一個在自己的請求驗證器丟出例外之後就停下來的框架，只測到了它自己，沒測到伺服器的線路行為。

官方的 MCP 一致性專案，很適合當成一套外部測試組與有版本的參照。你自己的逐字紀錄也要留著。它們擷取的是你的代理、SDK、認證、擴充與發布路徑，而那些是通用測試組不會知道的。

## 標頭值必須跟 RPC 本體相符

在現代的 Streamable HTTP 裡，中介可以用鏡像標頭做路由或執行政策。JSON-RPC 本體仍然是協定的真相來源。不一致是完整性失敗，不是「挑一個值」的提示。

依這個順序驗證：

1. 解析並驗證 JSON-RPC 信封與中繼資料的型別。
2. 把 `MCP-Protocol-Version` 跟 `params._meta.io.modelcontextprotocol/protocolVersion` 比較。
3. 把 `Mcp-Method` 跟 `method` 比較。
4. 當那個方法有路由名稱時，把 `Mcp-Name` 跟本體裡對應的值比較。
5. 在相等確立之後，再決定比對出來的版本與能力集合支不支援。

這個順序把不一致的 `-32020` 跟版本不支援的 `-32022` 分開。它也阻止閘道去授權標頭上的名稱，而源站執行的卻是本體裡另一個名稱。

HTTP 欄位名稱不分大小寫，而它們的值仍然分大小寫。查找之前先把標頭名稱正規化，並拒絕互相衝突的重複。對一個不安全、非 ASCII，或前後帶空白的 `Mcp-Name`，要先把那個確切的 `=?base64?{Base64EncodedValue}?=` UTF-8 哨符解碼，再拿去跟本體比較。哨符不完整、Base64 無效、UTF-8 無效，或原始的不安全值，都用 `-32020` 拒絕。原始的前後空白就是無效的，即使本體裡是同樣的字元也一樣，因為那個值在傳輸之前本來就該用哨符編碼。

中介可以在請求到達 MCP 伺服器之前，就把格式不對的 HTTP 擋掉，所以它的失敗可能是一個沒有 JSON-RPC 的 HTTP 錯誤。要擷取下來：這次拒絕是來自中介還是源站。當源站 MCP 伺服器處理的是一個有效的 JSON-RPC 請求時，它應該用協定錯誤契約。

## 未知欄位不是未知結果

向前相容需要兩條不同的規則。

### 可加的未知欄位

結果物件與 `_meta` 映射可以長出新欄位。驗證器應該依那個欄位的角色去保留或忽略它，除非該欄位違反了某個保留契約。範例把完整的原始結果留在證據裡，並接受一個跟在已知結果旁邊的 `futureHint`。

如果你是一個透明代理，保住未知欄位通常比把它剝掉安全。如果你是一個應用程式客戶端，忽略它可以是有效的。你的差異測試仍然應該把「SDK 把它省掉了」揭露出來，好讓那個行為是刻意的。

### 未知的 `resultType`

`resultType` 是一個判別子。核心的現代結果用 `complete` 或 `input_required`。擴充只有在它的能力被公告之後，才能加上另一個值。舉例來說，Tasks 擴充可以在那個協商好的能力脈絡下加上 `task`。

一個未知或未被公告的判別子，沒辦法被安全地當成 complete。客戶端並不知道它會丟掉的是什麼生命週期。把它擋掉。

因此同一份原始回應，可以同時含有一個可接受的未知欄位與一個不可接受的未知結果型別。兩種案例都要測。

判別子只是第一層。之後要驗證方法專屬的酬載。一份 complete 的 `tools/list` 結果需要一個 `tools` 陣列，它的描述子要有唯一且非空的名稱、有用的描述，以及以物件為根的 `inputSchema` 值。一份 `task` 結果只有在一次合格、且具備 Tasks 能力的 `tools/call` 上才有效，而且需要 `taskId`、已知的狀態、建立與更新的時間戳記與 `ttlMs`，外加一個有效的選配輪詢間隔。一份 complete 的 `completion/complete` 結果需要一個 `completion` 物件，裡面不超過 100 個字串值，一個選配的非負整數 `total`（不得小於回傳值的數量），以及一個選配的布林 `hasMore`。一個拼字正確的 `resultType`，救不了一份格式不對的酬載。

## 通知的不變條件

一則 JSON-RPC 通知沒有 `id`。接收方不得送出 JSON-RPC 的成功或錯誤回應。

對一個被接受的 HTTP 通知形狀，這個框架預期的是 HTTP `202` 加一個空本體。MCP `2026-07-28` 在 Streamable HTTP 上沒有定義任何核心的客戶端到伺服器通知。範例只用一個具命名空間的課程擴充通知來測那個單向序列化器的不變條件。不要把它說成一個新的核心方法。

要測的是序列化器，不只是處理器。處理器可以回傳 `None`，而中介軟體把它包成一個 JSON 成功物件。把最終送出去的位元組擷取下來。

## 加上 SDK 差異比對

SDK 常常把線路上的物件轉成方便的語言型別。那很有用，但一個正規化後的物件證明不了收到的是什麼。

對每一份高風險素材，都要擷取：

1. SDK 解碼之前的原始狀態、標頭與回應本體。
2. SDK 正規化後的回傳值或例外。
3. 針對選定紀元的預期語意投影。
4. 被 SDK 提升、合成、剝掉或改掉的欄位。

範例允許 SDK 單方面移除 `resultType`、`_meta`、`ttlMs` 與 `cacheScope` 這類已知的線路記帳欄位，同時比較應用程式酬載。它會回報 `futureHint` 被丟掉了，因為那個未知的語意欄位消失了。

不要假設每一個差異都是 SDK 的臭蟲。重點是讓那個轉換看得見。決定你的元件是一個可以忽略可加欄位的應用程式端點，還是一個應該保住它的透明中介。

對你出貨的每一個 SDK 與每一個版本都跑一次差異比對。如果兩個 SDK 對同一份逐字紀錄正規化出不同結果，發布政策應該說清楚哪一種行為可以接受，而不是事後挑一個最順手的輸出。

## 擷取代理證據

大多數生產環境的 MCP 失敗，跨的是不只一個行程。記下三種視圖：

| 視圖 | 最低限度的證據 |
|---|---|
| 入口 | 請求標頭、JSON-RPC 本體、content type、通過認證的路由、接收時間 |
| 源站 | 轉發的標頭與本體摘要、源站狀態、回應標頭與本體 |
| 出口 | 客戶端看得到的狀態、標頭、本體，以及送出時間 |

範例偵測兩種常見的轉換：

- 源站的 HTTP 400 或 404 JSON-RPC 錯誤變成一個通用的代理 500
- 出口的 JSON-RPC 本體跟源站的本體不同

再加上你部署專屬的斷言，涵蓋 content type、`Accept`、壓縮、請求範圍的 SSE、快取標頭與追蹤關聯。在政策允許時，把 TLS 終止的兩側都擷取下來。絕不要為了證明路徑就把憑證記進日誌。

## 在證據離開記憶體之前先遮蔽

遮蔽是一致性維運的一部分，不是之後的清理工作。在序列化、取雜湊、日誌、測試產物或失敗上傳之前就套用它。

範例會先把鍵名做大小寫摺疊、移除分隔符再比對，然後遞迴地替換 `Authorization`、`Cookie`、`Set-Cookie`、`X-Api-Key`、`accessToken`、`clientSecret`、`registrationAccessToken`、`token`、`password`、`secret` 與 `api_key` 這些鍵底下的值。正規化與拒絕清單必須用同一種形式，這樣 camelCase、連字號、底線與句點的變體才不會互相繞過對方的政策。生產環境的收集器還應該加上方法專屬的引數政策，因為像 `query` 這種看似無害的鍵，照樣可以裝著個資或受監管的資料。

替遮蔽後的證據包取雜湊。只有在某次具體調查需要時，才把原始擷取留在一個被核可、生命期很短的系統裡。摘要證明的是「哪一份遮蔽後的包驅動了這個決策」；它不會揭露被移除的值。

## 把健康狀態與回滾也納進關卡

協定一致性是發布的必要條件，但不是充分條件。一個合規的候選版本照樣可能逾時、漏記憶體，或把某個依賴壓垮。

在推出之前先定義一個健康觀察窗：

- 最低樣本數
- 最高錯誤率
- 延遲百分位的上限
- 飽和度或資源上限
- 觀察期長度
- 跟已准入的 baseline 做比較

在推出之前也先定義回滾證據：

- 確切的前一個版本
- 准入證據的摘要
- 產物與描述子的 SHA-256 釘選
- 當前的登錄庫狀態
- 當前的健康結果
- 路由還原的程序
- 由一個受信任的發布控制器身分，對上述那些確切欄位做出的認證

在推上去之前就要求那個回滾目標已驗證且健康，不是等候選版本掛了才要求。一次沒有可用復原路徑的成功發布，不算生產就緒。

如果候選版本失敗，而回滾目標缺少那些證據，就把流量壓住，不要用猜的。「回滾到本來那個」不是一項維運控制。

不要把就緒度縮成真值檢查，例如「版本非空」、`healthy: "yes"`，或一個隨便的證據字串。範例要求的是確切的型別、一個 active 的狀態、三個 SHA-256 摘要、一個受信任的簽署者，以及一份對完整回滾酬載做的有效 HMAC-SHA-256 認證。它那把決定性的示範金鑰是一份非機密的素材。在生產環境裡，請在發布邊界注入一把受保護的金鑰、一個 KMS 驗證結果，或一個公鑰認證驗證器。

發布關卡也會拒絕空的逐字紀錄、SDK 差異或代理證據。每一個來源都必須帶著有效的證據摘要。一個綠燈的健康觀察窗，補不上一道從來沒被觀察過的邊界。

## 動手實作

跑那個只用標準庫的框架：

```bash
cd phases/13-tools-and-protocols/31-mcp-conformance-versioning-and-operations
python3 code/main.py
```

這支示範會跑剛好十五份黃金與負向逐字紀錄，其中包含有效與格式不對的補全結果，會把一份原始結果跟一個 SDK 視圖比較、檢視一個把源站錯誤塌掉的代理、評估健康狀態、對回滾證據做身分驗證，並選定那個目標。

預期的形狀：

```json
{
  "transcriptsPassed": 15,
  "transcriptsTotal": 15,
  "sdkDroppedFields": ["futureHint"],
  "proxyIssues": [
    "proxy collapsed a protocol error into HTTP 500",
    "proxy changed the origin JSON-RPC body"
  ],
  "releaseAction": "rollback",
  "evidenceDigest": "..."
}
```

依這個順序讀 `code/main.py`：

1. `validate_request()` 強制執行紀元專屬的請求與標頭規則。
2. `validate_result()` 把缺漏的舊版判別子、有效的現代值、擴充與未知值分開。
3. `select_era()` 實作嚴格與有界退路的政策。
4. `run_transcript()` 評估黃金與負向素材。
5. `compare_sdk_view()` 把正規化的差異暴露出來。
6. `inspect_proxy()` 比較入口、源站與出口的證據。
7. `redact()` 在替證據取雜湊之前移除明顯的密鑰。
8. `rollback_evidence_ready()` 驗證那些確切的釘選欄位與受信任的發布認證。
9. `ReleaseGate.evaluate()` 把非空的一致性、SDK、代理、健康與回滾證據接起來。

## 框架應用

在四個時間點跑這個框架：

1. 每一次實作變更時，用一個行程內的測試轉接器跑。
2. 在真實傳輸上，對建好的客戶端與伺服器執行檔跑。
3. 在測試環境裡，穿過已部署的代理或閘道跑。
4. 在金絲雀推出期間，帶著即時的健康與回滾證據跑。

各層之間沿用同一組穩定的案例名稱。`negative-header-body-mismatch` 在單元、端到端、代理與金絲雀報告裡，都該指同一個不變條件。證據摘要會不一樣，因為邊界變了；但要求不該變。

把素材的 schema 放進版本控制。把遮蔽後的執行證據放進你的發布系統。原始擷取只在事故存取控制之下短期保存。

## 互動實驗

### 實驗 A：證明紀元邊界

從 `code` 目錄打開 Python：

```bash
cd phases/13-tools-and-protocols/31-mcp-conformance-versioning-and-operations/code
python3 -q
```

執行：

```python
from main import *
validate_result({"tools": []}, "legacy")
validate_result({"tools": []}, "modern")
```

舊版那次呼叫會推論成 `complete`。現代那次會丟出 `ProtocolViolation`。現在測退路：

```python
select_era({"kind": "timeout"}, "fallback")
select_era(
    {"kind": "timeout"},
    "fallback",
    legacy_allowed=True,
    legacy_evidence={"kind": "initialize_success", "protocolVersion": LEGACY_VERSION},
)
select_era({"kind": "jsonrpc_error", "code": -32021}, "fallback")
```

第一次逾時會失敗關閉，因為沉默不是舊版的證據。第二次呼叫之所以選了舊版，只是因為設定允許它，而且觀察到了一份有效的舊版初始化結果。那個已辨識的「缺少能力」錯誤則證明了現代分支。

### 實驗 B：可加欄位對判別子

```python
validate_result({"resultType": "complete", "tools": [], "futureHint": True}, "modern")
validate_result({"resultType": "future_mode", "tools": []}, "modern")
```

第一個結果保住了 `futureHint`。第二個被拒絕，因為那個生命週期判別子是未知的。

### 實驗 C：檢視一次 SDK 轉換

```python
compare_sdk_view(
    {"resultType": "complete", "tools": [], "futureHint": {"mode": "new"}},
    {"tools": []},
)
```

決定你的元件可以忽略 `futureHint`，還是必須把它轉發出去。把那個選擇寫進發布政策。不要默默把差異抹掉。

### 實驗 D：把代理修好

改掉示範裡的那次交換，讓出口保住源站的狀態與本體。再跑一次 `python3 main.py`。代理的問題應該消失，但 SDK 差異仍然會擋住推上去。接著把 `futureHint` 放進 SDK 視圖，觀察在每一個證據來源都通過時，動作會變成 `promote`。

## 練習實驗

替這個框架加上請求範圍的 SSE 逐字紀錄。

要求：

- 擷取回應狀態、content type、依序的 SSE 事件，以及串流的終止。
- 證明每一個 JSON-RPC 事件都有一個有效的、符合該紀元的結果或錯誤。
- 加一個負向案例：一個在轉發之前把整條串流緩衝起來的代理。
- 加一個負向案例：一個 JSON-RPC id 跟請求不同的 SSE 事件。
- 在寫出證據之前先把事件資料遮蔽。
- 把串流時長、首個事件的延遲與事件數量納進健康觀察窗。
- 讓發布關卡在串流失敗時，只選擇一個有證據的回滾目標。

成功的意思是：同一個案例能直連跑，也能穿過代理跑，而報告能指出到底是哪一道邊界改變了行為。

這一課出貨 `outputs/skill-mcp-conformance-release-gate.md`。用它把一次伺服器、客戶端、閘道或 SDK 的變更，變成一份有版本的一致性矩陣與一個發布決策。這份產物要求原始的線路證據、負向案例、明確的紀元選擇、SDK 差異、代理證明、遮蔽、健康門檻與回滾證據。

## 驗證成果

跑那個示範與那組決定性的測試：

```bash
cd phases/13-tools-and-protocols/31-mcp-conformance-versioning-and-operations
python3 code/main.py
python3 -m unittest discover -s code/tests -v
```

驗證應該證明：

- 每一份納入的黃金與負向逐字紀錄，都走到它預期的結果
- 現代請求要求那些確切的具命名空間中繼資料鍵
- HTTP 標頭名稱以不分大小寫的方式比對，而編碼過的 `Mcp-Name` 值會被精確解碼
- 標頭與本體不一致會回傳那個現代的不一致錯誤碼
- 回應的版本、ID、result 與 error 的互斥性、錯誤形狀，以及 HTTP 對映都會被驗證
- 方法專屬的工具清單、task 與補全酬載的要求都被強制執行
- 每一次觀察到的 `HeaderMismatch`，都要求一個實際的 HTTP 400 JSON-RPC `-32020` 回應
- 原始的 `Mcp-Name` 空白會被拒絕，而精確以哨符編碼的空白能原樣來回
- 缺少 `resultType` 只有在選定的舊版紀元裡才有效
- 可加欄位能通過原始驗證，而未知的結果型別會失敗
- 擴充的結果型別需要它被公告過的能力
- 已辨識的現代錯誤，永遠不會造成舊版退路
- 通知不產生任何 JSON-RPC 回應
- SDK 的記帳欄位移除，跟語意欄位遺失是分得開的
- 代理的錯誤塌陷被偵測出來，而憑證在 camelCase 與各種分隔符變體上都被遞迴遮蔽
- 推上去需要非空的逐字紀錄、SDK、代理，以及健康的維運證據
- 推上去與回滾都需要一個經過身分驗證、已釘選、active 且健康的回滾目標

## 生產環境的失敗模式

| 失敗 | 弱測試回報什麼 | 框架必須證明什麼 |
|---|---|---|
| SDK 合成了一個缺漏的判別子 | 「tools/list 通過」 | 原始的現代結果缺少 `resultType`，因此無效 |
| 客戶端在 `-32021` 之後降級 | 「舊版重試成功」 | 已辨識的現代錯誤禁止退路 |
| 未知結果型別被當成 complete | 「回應解析成功」 | 未被公告的生命週期判別子被拒絕 |
| 代理授權了一項工具，源站執行了另一項 | 「請求到達伺服器」 | 每一跳的 `Mcp-Name` 都等於本體裡的路由名稱 |
| 框架在讀伺服器回應之前就丟例外 | 「標頭不一致測試通過」 | HTTP 400 與 JSON-RPC `-32020` 回應都被擷取並驗證 |
| 代理把源站的 400 變成通用的 500 | 「上游錯誤」 | 源站與出口的狀態與 JSON-RPC 本體都被保住 |
| 通知的中介軟體送出 `{result: null}` | 「處理器回傳 none」 | 最終送出的本體是空的，而且沒有任何 JSON-RPC 回應 |
| SDK 剝掉一個可加欄位 | 「有型別的物件相符」 | 原始與正規化的視圖顯示出被丟掉的確切欄位 |
| 失敗產物洩漏了一個 bearer 權杖 | 「除錯包已上傳」 | 遮蔽發生在取雜湊、記錄或上傳之前 |
| 憑證鍵的寫法繞過了遮蔽 | 「拒絕清單裡有 api_key」 | CamelCase 與分隔符變體共用同一種正規形式的拒絕清單 |
| 金絲雀沒有樣本卻看起來健康 | 「零錯誤」 | 最低樣本數有被強制 |
| 回滾選到一個未知的建置 | 「上一次部署已還原」 | 目標版本、准入摘要、釘選、狀態與健康狀態都在 |

## 維運準則

測你送出去的位元組、測每一個中介轉發的位元組、測每個 SDK 暴露出來的語意，也測維運在壓力之下會用到的那些證據。相容性是一條明確的分支。回滾是一項有證據支撐的發布動作。這兩者都不該是一個寬鬆解析器的意外副作用。
