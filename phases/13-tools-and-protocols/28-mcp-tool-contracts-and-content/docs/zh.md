# MCP 工具契約與內容

> 一項工具要能安全地自動化，前提是發現、引數、結果、分頁與傳輸中繼資料，全都同意同一份契約。

**類型：** 實作
**程式語言：** Python
**先修單元：** 階段 13 第 07、09 與 10 課
**時間：** 約 120 分鐘

## 學習目標

- 用 JSON Schema 2020-12 定義工具的輸入與輸出。
- 驗證有結構的結果，而不假設它們是 JSON 物件。
- 在文字、圖片、音訊、資源連結與內嵌資源之間做選擇。
- 在一項工具送到模型面前之前，先擋掉不安全的 `x-mcp-header` 定義。
- 把參數標頭的值編碼，並驗證標頭與本體完全一致。
- 走過游標分頁，而不去解讀游標的值。
- 對 `completion/complete` 的建議設上限並做授權。

## 問題所在

呼叫一個 Python 函式很容易。透過一個 AI 宿主呼叫一項遠端能力，是一個契約問題。

伺服器發布一份描述子。客戶端把那份描述子變成模型上下文與使用者介面。模型造出引數。閘道可能依鏡像標頭來路由這個請求。伺服器執行這項工具。客戶端接著決定這份結果夠不夠安全、夠不夠有效，能不能交回給模型。

一道邊界弱掉，整條鏈就壞了。

看五種失敗：

- 描述子說結果是物件，但伺服器回傳了一個陣列。
- 當 `nextCursor` 是空字串時，客戶端就停止分頁。
- 一個 token 參數被鏡像進 HTTP 標頭，於是被中介看見。
- 一個 Unicode 的路由值以原始標頭送出，接著閘道與源站解讀到不同的位元組。
- 一個補全端點把生產環境建議給了一個沒有權限存取它的呼叫方。

這些失敗沒有一個是靠更好的提示詞修得掉的。它們需要明確的協定契約與應用程式契約。

## 契約流水線

把每一次工具呼叫都當成五道閘門：

1. **發現。** 讀一份確定的、分頁的工具清單。
2. **准入。** 驗證每一份描述子，並套用本地的安全政策。
3. **叫用。** 驗證引數，並組出傳輸中繼資料。
4. **執行。** 跑處理器，並把失敗正確分類。
5. **消費。** 在模型使用之前先驗證內容區塊與有結構的輸出。

```figure
mcp-contract-pipeline
```

准入與消費這兩道閘門屬於宿主。伺服器沒辦法強迫客戶端信任它的註記、schema 或輸出。

## JSON Schema 是一道執行期邊界

在 MCP `2026-07-28` 裡，`inputSchema` 與 `outputSchema` 用的是 JSON Schema。當 `$schema` 缺席時，預設的方言是 2020-12。

輸入 schema 必須是一個 schema 物件。一項沒有引數的工具，仍然應該把它接受什麼說清楚：

```json
{
  "type": "object",
  "additionalProperties": false
}
```

這比 `{ "type": "object" }` 嚴，後者接受任意屬性。

輸出 schema 是選配的。一旦伺服器發布了一份，每一份完整的工具結果就承諾要回傳符合它的 `structuredContent`，包含 `isError: true` 的結果。錯誤旗標分類的是執行結果；它不會免除已發布的輸出契約。客戶端應該驗證結果，而不是信任描述子。

### 有結構的內容可以是任何 JSON 值

不要把 `structuredContent` 寫死成字典。它可以是：

- 一個物件；
- 一個陣列；
- 一個字串；
- 一個數字；
- 一個布林值；
- `null`。

這項工具回傳一個陣列：

```json
{
  "name": "tag_catalog",
  "inputSchema": {
    "type": "object",
    "additionalProperties": false
  },
  "outputSchema": {
    "type": "array",
    "items": {"type": "string"}
  }
}
```

它成功時的結果是有效的：

```json
{
  "resultType": "complete",
  "content": [
    {
      "type": "text",
      "text": "[\"contracts\", \"mcp\", \"stateless\"]"
    }
  ],
  "structuredContent": ["contracts", "mcp", "stateless"],
  "isError": false
}
```

為了相容性，有結構的結果也應該在一個文字區塊裡附上序列化後的 JSON。文字不是驗證的來源。`structuredContent` 才是。

### 一個小驗證器照樣教得出這道邊界

這一課刻意只用 JSON Schema 的一個子集，因為那樣才待得住 Python 標準庫之內。它檢查那些範例工具用到的機制：

- object、array、string、integer、number、boolean 與 null 這些型別；
- 必填屬性；
- `additionalProperties: false`；
- 陣列的 items；
- enum 的值；
- 字串的最小長度。

這取代不了一個完整的生產級驗證器。可以帶走的一課是「驗證發生在哪裡」：描述子在發現之後驗、引數在執行之前驗、有結構的結果在消費之前驗。

## 內容區塊帶著不同的成本

`content` 陣列可以混用好幾種內容型別。

| 型別 | 用它來裝 | 主要邊界 |
|------|------------|---------------|
| `text` | 人與模型讀得懂的摘要 | 把文字當成不可信的輸出 |
| `image` | 以 base64 編碼的視覺證據 | 驗證媒體型別與大小 |
| `audio` | 以 base64 編碼的語音或錄音輸出 | 驗證媒體型別與時長上限 |
| `resource_link` | 客戶端稍後可以去取的一個 URI | 對稍後那次資源讀取重新授權 |
| `resource` | 直接內嵌在結果裡的資料 | 現在就強制酬載與內容上限 |

一個資源連結不能證明那個資源會出現在 `resources/list` 裡。它是這一次工具呼叫回傳的一個參照。客戶端在跟隨那個 URI 時，仍然要套用它的資源政策。

內嵌資源省掉一次來回，但會撐大當前回應的大小。大的、或會獨立變動的產物，用連結。必須跟結果原子地一起走的小證據，用內嵌資源。

這一課的 `evidence_bundle` 結果把五種型別都用上了。客戶端在接受這份結果之前，會逐一驗證每個區塊。

## `x-mcp-header` 是路由中繼資料

`inputSchema` 裡的某個屬性可以宣告 `x-mcp-header`。在 Streamable HTTP 上，客戶端會把那個引數鏡像進 `Mcp-Param-{name}`。

```json
{
  "region": {
    "type": "string",
    "x-mcp-header": "Region"
  }
}
```

當 `region: "eu-west"` 時，傳輸可以送出：

```http
Mcp-Param-Region: eu-west
```

這個註記存在的目的，是讓負載平衡器、閘道或政策引擎不必解析 JSON 本體就能路由。它不是放憑證的地方。

協定對這個註記有限制：

- 標頭名稱非空，並符合 HTTP 欄位名稱的 token 語法；
- 標頭名稱不分大小寫都必須唯一；
- 屬性型別是 string、integer 或 boolean；
- 不允許 `number`；
- 這個註記只出現在 `inputSchema.properties` 的直接成員上；
- 整數值要落在 `-9007199254740991` 到 `9007199254740991` 之間。

那條位置規則是語法上的，而且失敗關閉。要走過整棵 schema 樹，不是只走你的驗證器剛好懂的那些屬性。要擋掉出現在嵌套物件的 `properties`、`oneOf` 分支、`items`、透過 `$ref` 到達的定義，或任何輸出 schema 底下的註記。解析一個參照，並不會把被參照的節點變成一個直接的最上層屬性。

這一課再加上一條部署政策：擋掉那些鏡像了 `password`、`secret`、`token`、`api_key` 或 `authorization` 這類名稱的描述子。官方規格建議伺服器作者不要鏡像敏感參數。客戶端可以把那條建議變成一條硬性的准入規則。

要稽核的是標頭名稱，不是它的值。範例程式碼記下 `Mcp-Param-Region`，同時把 `eu-west` 留在稽核事件之外。

### 在組 HTTP 標頭之前先把值編碼

只有當一個參數值是非空字串、而且只由 `!` 到 `~` 之間的可見 ASCII 字元組成、又不像那個編碼哨符時，它才可以用純文字送出。其他一律用這個確切的形式：

```text
=?base64?{Base64UTF8}?=
```

`Base64UTF8` 是對確切的 UTF-8 位元組做標準 base64。不要先修剪、正規化或替換那個值。Unicode、空字串、空格、tab、控制字元、CR 或 LF、前後空白，以及任何以 `=?base64?` 開頭的值，都要編碼。把一個看起來像哨符的值再編碼一次，正是接收端能還原出字面原文、而不是把它當成傳輸語法去解碼的原因。

布林值渲染成小寫的 `true` 或 `false`。整數用十進位渲染，而且必須待在 JavaScript 的安全整數範圍內。超出那個範圍的值會被拒絕，而不是被某個中介四捨五入。

### 伺服器要檢查那份鏡像副本

產生標頭只是客戶端那一半。在 Streamable HTTP 的邊界上，伺服器必須：

1. 不分大小寫地找出它認得的 `Mcp-Param-*` 名稱；
2. 在出現那個 base64 哨符形式時，把它精確解碼；
3. 把解碼後的文字跟 JSON 本體裡對應的引數做完全比對；
4. 在派送之前，就擋掉缺漏、重複、非預期、格式不對，或對不上的已辨識標頭。

拒絕的形式是 HTTP `400` 加上 JSON-RPC 錯誤碼 `-32020`。本體的值與它編碼後的標頭形式，都不屬於稽核紀錄。只記下那個已辨識的標頭名稱與拒絕的類別。

`code/main.py` 直接對這道邊界建模。[第 09 課](../../09-mcp-transports/)涵蓋更廣的 Streamable HTTP 驗證順序，包含方法與協定版本的一致性。

## 分頁游標是不透明的

MCP 的列表操作用的是游標分頁。頁面大小與游標格式由伺服器決定。客戶端只有一個決定：

```python
if result.get("nextCursor") is None:
    break
cursor = result["nextCursor"]
```

不要寫成這樣：

```python
if not result.get("nextCursor"):
    break
```

空字串是一個有效的游標。用真值判斷會太早停下。

客戶端不可以把游標解碼、把它遞增、拿它跟先前的游標比較順序，或從它推論頁碼。伺服器可以替游標簽章、把它綁到某個目錄版本，或把它映射到私有狀態。那是伺服器的實作細節。

範例伺服器刻意在第一頁之後回傳 `""`。客戶端必須在第二個請求裡送出那個確切的值。它的追蹤是：

```text
<first request with no cursor>
<second request with cursor "">
```

無效的游標會產生 JSON-RPC 的無效參數，錯誤碼 `-32602`。

## 補全是一道授權面

`completion/complete` 替提示詞引數與資源樣板引數提供建議。它對互動式表單很有用，但它可能洩漏那些一般列表方法保護著的名稱。

一個補全請求會指名一個參照與正在被補全的引數：

```json
{
  "method": "completion/complete",
  "params": {
    "ref": {
      "type": "ref/prompt",
      "name": "deployment_review"
    },
    "argument": {
      "name": "environment",
      "value": "st"
    }
  }
}
```

結果最多回傳 100 個值，並且可以回報 `total` 與 `hasMore`。

套用被參照的那個提示詞或資源所用的同一道授權邊界。範例裡的分析師會收到 `development` 與 `staging`。只有維運人員才收得到 `production`。

生產環境的補全還需要：

- 輸入驗證；
- 依呼叫方而異的過濾；
- 客戶端的請求防抖；
- 伺服器端的速率限制；
- 有上限的結果數量；
- 不會把敏感建議值暴露出來的日誌。

補全是輔助，不是繞過發現的後門。

## 兩層錯誤

把協定錯誤跟工具執行錯誤分開。

當一個 MCP 請求沒辦法被正確派送時，用 JSON-RPC 錯誤：

- 未知的工具名稱；
- 格式不對的請求形狀；
- 缺漏的請求中繼資料；
- 無效的游標。

當叫用已經到達工具、而工具回報一個可據以行動的失敗時，用一份帶 `isError: true` 的完整工具結果：

- 某個報表來源不可用；
- 某個日期超出支援範圍；
- 某條業務規則拒絕了被請求的操作。

模型常常修得好一個工具執行錯誤。它們修不好一台違反自己輸出 schema 的伺服器。

如果這項工具宣告了輸出 schema，就把可據以行動的失敗建模在那個 schema 之內。範例的 `route_report` 失敗會回傳它被請求的 region，並帶 `accepted: false`，同時附上人類讀得懂的錯誤文字與 `isError: true`。

## 動手實作

`code/main.py` 用 Python 標準庫把這道邊界的兩邊都建了起來。

伺服器實作了：

- 逐請求的 MCP 中繼資料驗證；
- 帶 tools 與 completions 能力的 `server/discover`；
- 確定的 `tools/list` 分頁；
- 四份工具描述子，其中一份必須被拒絕；
- 陣列形式的有結構輸出；
- 現行的每一種工具內容區塊型別；
- 一道 Streamable HTTP 一致性閘門，它會解碼已辨識的參數標頭，並在對不上時回傳 HTTP `400` 加 JSON-RPC `-32020`；
- 有授權且有速率限制的補全。

客戶端實作了：

- 描述子准入；
- 走完整棵樹的 `x-mcp-header` 位置驗證，以及敏感欄位政策；
- 精確的純可見 ASCII 或 base64 UTF-8 值編碼；
- 一個會跟隨空字串的不透明游標迴圈；
- 引數與結果驗證；
- 內容區塊驗證；
- 只含名稱、不含值的標頭稽核事件。

那份刻意做壞的描述子是教學資料。它證明一項被拒絕的工具，不會害得其他有效的工具載不進來。


## 互動實驗

打開 `code/main.py`，找到 `TOOLS`。

1. 把 `tag_catalog.outputSchema.type` 從 `array` 改成 `object`。
2. 跑示範。客戶端應該拒絕那個回傳的陣列。
3. 把 schema 改回去。
4. 讓第一頁的 `nextCursor` 維持 `""`，然後讓最後一頁回傳 `nextCursor: None`，而不是省略這個欄位。
5. 跑測試，並比較游標的追蹤。
6. 在某個字串屬性上加 `x-mcp-header: "Authorization"`。
7. 確認描述子准入會在叫用之前就把它擋掉。
8. 試試含 Unicode、換行、前後空格，以及字面文字 `=?base64?SGVsbG8=?=` 的 `region` 值。把送出的每一個標頭解碼，證明原值一字不差地活下來。
9. 把那個註記搬到 `oneOf`、`items` 或某個 `$ref` 定義底下。確認就算示範根本沒用到那個分支，每一份描述子還是被拒絕。
10. 拿掉那個已辨識的標頭，或改掉它解碼後的值。確認 HTTP 邊界回傳狀態 `400` 與 JSON-RPC 錯誤碼 `-32020`。

重點不是把某個 JSON 形狀背下來。重點是親眼看見每一道閘門，都在該負責它的那道邊界上失敗。

## 練習實驗

替這個契約實驗加上一項 `search_evidence` 工具。

要求：

1. 它的輸入 schema 接受 `query`、`limit`，以及一個安全的 `region` 路由欄位。
2. 它的輸出 schema 是一個物件陣列，每個物件有 `uri`、`title` 與 `score`。
3. 結果包含相容性文字，以及每一項的資源連結。
4. 引數會拒絕未知屬性。
5. `limit` 由應用程式驗證設上限。
6. 一個沒有某個 URI 存取權的呼叫方，永遠不會透過補全或工具輸出看到那個 URI。
7. 測試包含一個不符規範的 score、一個無效的標頭註記，以及一份兩頁的清單。
8. 標頭值的測試涵蓋可見 ASCII、Unicode、控制字元、空白、看起來像哨符的文字，以及 JavaScript 安全整數的上下界。
9. HTTP 測試素材接受不分大小寫的標頭名稱，但對缺漏或對不上的已辨識值，回傳狀態 `400` 與錯誤碼 `-32020`。

## 出貨產物

`outputs/skill-mcp-contract-reviewer.md` 是一個扁平、可重用的審查技能。給它一份工具描述子、範例結果、分頁行為與補全政策。它會回傳一個准入決定、一份結果驗證計畫、一套標頭政策，以及具體的失敗測試。

## 驗證成果

當下列敘述都成立時，這一課就完成了：

- 重複呼叫 `tools/list` 會回傳同樣的邏輯順序。
- 當 `nextCursor` 是 `""` 時，客戶端會發出第二個請求。
- 那份不安全的敏感標頭描述子被排除，而其他工具仍然可用。
- 一個陣列能通過它的陣列輸出 schema。
- 一個物件通不過同一份陣列 schema。
- 錯誤結果不能省略或違反已發布的輸出 schema。
- 文字、圖片、音訊、資源連結與內嵌資源區塊都驗得過。
- 標頭稽核事件裡有名稱、沒有值。
- 純可見 ASCII 維持純文字；Unicode、控制字元、有前後空白、空字串，以及看起來像哨符的值，都能透過精確的 base64 UTF-8 編碼原樣來回。
- 超出 JavaScript 安全範圍的鏡像整數會被拒絕。
- 出現在 `oneOf`、`items`、嵌套物件、`$ref` 定義或輸出 schema 底下的註記，會在准入時被拒絕。
- 不分大小寫的已辨識標頭名稱，只有在解碼後的值跟本體完全相符時才通過；缺漏或對不上的副本會產生 HTTP `400` 與 JSON-RPC `-32020`。
- 分析師的補全永遠不會回傳 `production`。
- 工具失敗用 `isError: true`；格式不對的協定呼叫用 JSON-RPC 的 `error`。

## 生產環境的失敗模式

| 失敗 | 學習者看到什麼 | 正確的回應 |
|---------|-----------------------|------------------|
| 客戶端假設輸出是物件 | 有效的陣列失敗，或被默默包起來 | 對照已發布的 schema 驗證，不要只認物件型別 |
| 空游標被當成假值 | 最後幾頁消失 | 只要 `nextCursor` 存在且非 null 就繼續 |
| 敏感值被鏡像 | 密鑰出現在代理、WAF 或追蹤資料裡 | 拒絕那份描述子，並把密鑰留在受保護的請求資料裡 |
| 原始 Unicode 或空白被鏡像 | 閘道與源站看法不一致，或值被正規化 | 用精確的 base64 UTF-8 哨符編碼，並在解碼後比較 |
| 註記藏在某個 schema 分支裡 | 客戶端在准入時漏掉路由中繼資料 | 走遍整棵 schema 樹，只允許直接的最上層屬性 |
| 大整數被鏡像 | JavaScript 中介把路由值四捨五入 | 拒絕超出 JavaScript 安全整數範圍的值 |
| 標頭與本體不一致 | 閘道路由到一個目標，源站卻執行另一個 | 在派送之前就用 HTTP `400` 與 JSON-RPC `-32020` 拒絕 |
| 輸出 schema 被忽略 | 下游程式碼吃到壞掉的結構 | 在模型或應用程式使用之前先驗證 |
| 資源連結被自動信任 | 呼叫方跟到一個沒授權的 URI | 對每一次資源讀取重新授權 |
| 補全共用全域建議 | 隱藏的租戶名稱外洩 | 依呼叫方、參照與授權過濾 |
| 工具註記被當成政策 | 破壞性操作繞過了確認 | 在註記之外強制授權與核可 |
| 一份壞掉的工具弄壞整個發現 | 整台伺服器變得不可用 | 拒絕那份壞描述子，並獨立准入有效的工具 |

## 與總結專案的連結

階段 13 的總結專案需要一個能把多台伺服器的工具合併起來的閘道。這一課提供它的准入核心。

用這份產物去評分總結專案的四項證據：

- 確定且完整的分頁發現；
- 在暴露給模型之前的描述子驗證；
- 通過驗證的有結構輸出，加上有上限的內容區塊；
- 能保住授權邊界的補全與路由中繼資料。

不要只憑一次成功的 `tools/call` 就宣稱閘道相容。把描述子、分頁追蹤、被准入的工具集、被拒絕的工具集，以及一份通過驗證的結果都擷取下來。

## 關鍵術語

| 術語 | 意思 |
|------|---------|
| `inputSchema` | 定義可接受工具引數的 JSON Schema 物件 |
| `outputSchema` | 定義 `structuredContent` 的選配 JSON Schema |
| `structuredContent` | 一份工具結果產出的任何 JSON 值 |
| 內容區塊 | 有型別的文字、圖片、音訊、資源連結或內嵌資源 |
| `x-mcp-header` | 把一個原始型別引數鏡像進 Streamable HTTP 中繼資料的 schema 註記 |
| 不透明游標 | 由伺服器簽發、客戶端不去解讀其值的分頁權杖 |
| 補全參照 | 正在被補全的那個引數所屬的提示詞名稱或資源 URI／樣板 |
| 准入 | 客戶端決定要暴露還是拒絕一份被發現的描述子 |
