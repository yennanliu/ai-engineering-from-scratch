# 工具介面 —— 為什麼代理需要結構化 I/O

> 語言模型產出詞元。程式採取動作。這兩者之間的落差就是工具介面：一份讓模型能請求動作、讓宿主能執行動作的契約。2026 年的每一套堆疊 —— OpenAI、Anthropic 與 Gemini 上的函數呼叫；MCP 的 `tools/call`；A2A 的 task part —— 都是同一個四步驟迴圈的不同編碼。這一課會替這個迴圈命名，並展示跑起它所需的最小機件。

**類型：** 學習
**程式語言：** Python (stdlib, no LLM)
**先修單元：** 階段 11（LLM 補全 API）
**時間：** 約 45 分鐘

## 學習目標

- 說明為什麼一個只會生成文字的 LLM，光靠自己無法對真實世界採取動作。
- 畫出四步驟的工具呼叫迴圈（描述 → 決定 → 執行 → 觀察），並指出每一步由誰負責。
- 把一份工具描述寫成三個部分：名稱、JSON Schema 輸入，以及一個確定性的執行器函式。
- 區分純粹工具與有副作用的工具，並說明這個劃分為什麼攸關安全。

## 問題所在

一個 LLM 吐出的是下一個詞元的機率分布。那就是它輸出的全部表面積。如果你問一個聊天模型「Bengaluru 現在天氣如何」，它能寫出一句貌似合理的話，但它撥不進天氣 API。那句話可能碰巧是對的，也可能已經過期三天。

補上那道落差，就是工具介面的目的。宿主程式 —— 你的代理執行環境、Claude Desktop、ChatGPT、Cursor，或一個客製腳本 —— 向模型公告一份可呼叫的工具清單。當模型判斷需要採取動作時，它就吐出一份結構化酬載，指名工具與參數。宿主解析那份酬載、真的把工具跑起來，再把結果餵回去。這個迴圈持續下去，直到模型判斷不需要再呼叫為止。

這份契約的第一個版本，在 2023 年 6 月以 OpenAI 的「functions」參數出貨。Anthropic 隨後在 Claude 2.1 推出 `tool_use` 區塊。Gemini 幾個月後加上了 `functionDeclarations`。現在每家供應商都暴露同樣的形狀：進去的是一份以 JSON Schema 定型的工具清單，出來的是一份 JSON 酬載的工具呼叫。Model Context Protocol（2024 年 11 月）把這份契約一般化，讓單一份工具登錄就能服務所有模型。A2A（2026 年 4 月，v1.0）則把同樣的原語疊到代理對代理的委派上。

四步驟迴圈就是這一切底下的不變量。階段 13 的其他一切，都只是它的展開。

## 核心概念

### 第一步：描述

宿主用三個欄位宣告每個工具。

- **名稱。** 一個穩定、機器可讀的識別字。是 `get_weather`，不是「天氣那個東西」。
- **描述。** 一段自然語言的使用簡報。「當使用者詢問特定城市的當前狀況時使用。不要用於歷史資料。」
- **輸入 schema。** 一個描述工具參數的 JSON Schema 物件（draft 2020-12）。

模型收到這份清單。現代供應商會用各自的模板，把這些宣告序列化進系統提示詞裡，所以身為呼叫方的你只需要面對結構化的那一份。

### 第二步：決定

給定使用者的訊息與可用的工具，模型會選擇三種行為之一。

1. **直接用文字回答。** 不呼叫工具。
2. **呼叫一或多個工具。** 吐出結構化的呼叫物件。在 `parallel_tool_calls: true` 之下（OpenAI 與 Gemini 預設開啟，Anthropic 需自行選用），模型可以在一輪中吐出多次呼叫。
3. **拒絕。** 嚴格模式的結構化輸出可以產生一個定型的 `refusal` 區塊，而不是一次呼叫。

一份工具呼叫酬載有三個穩定欄位：呼叫的 `id`、工具的 `name`，以及一個 JSON 的 `arguments` 物件。那個 id 的存在，是為了讓宿主能把之後的結果對應回特定的那次呼叫 —— 當平行呼叫亂序回來時，這件事就很要緊。

### 第三步：執行

宿主收到呼叫，拿參數去對宣告的 schema 驗證，然後跑執行器。參數無效意味著模型幻覺出一個欄位，或用錯了型別 —— 在弱模型上這是非常常見的失敗模式。生產級宿主碰到無效參數時會做三件事之一：快速失敗並把錯誤呈現給模型、用受限解析器修復那份 JSON，或把驗證錯誤附進提示詞再讓模型重試。

執行器本身就是普通的程式碼。Python、TypeScript、一道 shell 指令、一次資料庫查詢。它產出一個結果，通常是字串，但也可以是任何 JSON 值或一個結構化的內容區塊（MCP 中的文字、影像或資源參照）。這個結果必須是可序列化的。

### 第四步：觀察

宿主把工具結果附加到對話中（成為一則帶對應 `id` 的 `tool` 角色訊息），然後重新呼叫模型。模型此刻的上下文裡有了工具輸出，於是可以產出最終答案，或請求更多呼叫。這會持續下去，直到模型不再吐出呼叫，或宿主碰到迭代次數的安全上限。

### 信任的劃分

工具有兩種風味，而這個區別攸關安全。

- **純粹。** 唯讀、確定性、沒有副作用。`get_weather`、`search_docs`、`get_current_time`。可以放心地投機呼叫。
- **有後果。** 會變更狀態、花錢、碰到使用者資料。`send_email`、`delete_file`、`execute_trade`。必須設閘門。

Meta 在 2026 年提出的代理安全「二選二規則」說：單一輪次最多只能同時包含以下三者中的兩者：不可信輸入、敏感資料、有後果的動作。工具介面正是你落實這條規則的地方 —— 靠拒絕呼叫、要求使用者確認，或提升權限範圍。完整的安全章節見階段 13 · 15，代理層級的權限政策見階段 14 · 09。

### 這個迴圈住在哪裡

| 情境 | 誰負責描述 | 誰負責決定 | 誰負責執行 |
|---------|---------------|-------------|--------------|
| 單輪函數呼叫（OpenAI／Anthropic／Gemini） | 應用開發者 | LLM | 應用開發者 |
| MCP | MCP 伺服器 | 透過 MCP 客戶端的 LLM | MCP 伺服器 |
| A2A | Agent Card 的發布者 | 發起呼叫的代理 | 被呼叫的代理 |
| 網頁瀏覽器（函數呼叫代理） | 瀏覽器擴充套件／WebMCP | LLM | 瀏覽器執行環境 |

處處都是同樣那四步。欄位名稱會變；結構不會。

### 為什麼不乾脆叫模型吐出 JSON 就好？

「請模型用 JSON 回覆」是函數呼叫出現之前的做法。它在前沿模型上大約有 5% 到 15% 的失敗率，在小模型上高得多。失敗模式包括缺大括號、多餘逗號、幻覺欄位與錯誤型別。你接著就需要一輪 JSON 修復、一次重試，或一個受限解碼器。

原生的函數呼叫更好，有三個理由。第一，供應商用確切的呼叫形狀端到端訓練過模型，所以在嚴格模式下有效 JSON 的比率會爬到 98% 到 99%。第二，呼叫酬載坐在它自己的協定欄位裡，不在自由文字內 —— 所以工具呼叫絕不會漏進使用者看得到的回覆。第三，供應商用受限解碼強制 schema 合規（OpenAI 的嚴格模式、Anthropic 的 `tool_use`、Gemini 的 `responseSchema`）。輸出保證能通過驗證。

### 斷路器

當模型不再吐出呼叫，或宿主碰到最大輪數時，迴圈就終止。生產級宿主會把這個值設在 5 到 20 輪之間。超過那個範圍，你幾乎肯定是陷在一個模型出不來的迴圈裡。Claude Code 預設 20；OpenAI Assistants 是 10；Cursor 的代理模式是 25。

另一種做法 —— 無界迴圈 —— 每半年就會以「代理一夜之間燒掉 400 美元 API 費用」的事後檢討報告形式出現一次。不要在沒有上限的情況下出貨。

階段 14 · 12 深入談錯誤復原與自我修復；階段 17 談生產環境的速率限制。

## 框架應用

`code/main.py` 不靠 LLM 就跑起那個四步驟迴圈。一個假的「決策器」函式靠比對使用者訊息的模式來模擬模型；執行器、schema 驗證器與觀察步驟的測試框架則是真的。跑跑看，你會看到完整的請求／回應編排，還有可印出的中間狀態；之後的單元再把那個假決策器換成任何真正的供應商。

要看的地方有：

- 工具登錄每個工具存三個欄位：名稱、描述、schema，以及一個執行器參照。
- 那個驗證器只實作 JSON Schema 的最小子集（型別、required、enum、min/max），純 stdlib 寫成。階段 13 · 04 會出貨一個更完整的。
- 迴圈把迭代次數限制在五次。生產級代理需要的正是這種斷路器。

## 產出交付

這一課產出 `outputs/skill-tool-interface-reviewer.md`。給定一份工具定義草稿（名稱 + 描述 + schema + 執行器綱要），這項技能會稽核它適不適合這個迴圈：名稱在機器層面穩定嗎、描述是不是一份完整的使用簡報、schema 有沒有正確使用 JSON Schema 2020-12，以及純粹對有後果的分類有沒有寫明。

## 練習

1. 在 `code/main.py` 加上第四個工具，叫做 `get_stock_price(ticker)`。把它的描述寫成「當使用者依代號詢問當前股價時使用。不要用於歷史股價或市場摘要。」跑一次測試框架，確認那個假決策器會把提到代號的查詢導向新工具。

2. 把 schema 驗證器弄壞。傳入一個 `arguments` 物件缺少必填欄位的呼叫，確認宿主在執行之前就把它擋下。接著傳入一個帶有多餘未知欄位的呼叫。決定：宿主該拒絕還是忽略？用一個安全上的論據為你的選擇辯護。

3. 把測試框架裡的每個工具分類成純粹或有後果。替需要的登錄項目加上 `consequential: true` 旗標，並修改迴圈，讓它在選到有後果的工具時印出一行「將向使用者確認」。這就是每個生產級宿主都需要的那道確認閘門的形狀。

4. 在紙上畫出那個四步驟迴圈，並把上面那張供應商欄位表填成你最愛的客戶端（Claude Desktop、Cursor、ChatGPT，或一套客製堆疊）。再與階段 13 · 06 中 MCP 專屬的變體交叉比對。

5. 把 OpenAI 的函數呼叫指南從頭讀到尾。找出那個存在於請求中、卻不在本課所呈現的四步驟迴圈裡的欄位。說明它添加了什麼，以及為什麼它只是方便，而非必要。

## 關鍵術語

| 術語 | 大家怎麼說 | 實際上是什麼 |
|------|----------------|------------------------|
| 工具 | 「模型可以呼叫的東西」 | 一組三元組：名稱 + 以 JSON Schema 定型的輸入 + 執行器函式 |
| 函數呼叫 | 「原生工具使用」 | 供應商層級的 API 支援，讓模型吐出結構化的工具呼叫而非散文 |
| 工具呼叫 | 「模型請求行動」 | 由模型吐出、帶 `id`、`name`、`arguments` 的 JSON 酬載 |
| 工具結果 | 「工具回傳了什麼」 | 執行器的輸出，包在一則 id 相符的 `tool` 角色訊息裡 |
| 平行工具呼叫 | 「一次呼叫很多個」 | 同一輪模型輸出裡的多個呼叫物件，彼此獨立且可依 id 排序 |
| 嚴格模式 | 「保證是 JSON」 | 用受限解碼強迫模型輸出通過所宣告 schema 的驗證 |
| 純粹工具 | 「唯讀工具」 | 沒有副作用；重跑也安全 |
| 有後果的工具 | 「動作型工具」 | 會變更外部狀態；需要閘門、稽核或使用者確認 |
| 四步驟迴圈 | 「工具呼叫週期」 | 描述 → 決定 → 執行 → 觀察 |
| 宿主 | 「代理執行環境」 | 持有工具登錄、呼叫模型並執行執行器的那個程式 |
