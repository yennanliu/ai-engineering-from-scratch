# MCP 的可靠性、取消與流量控制

> 一個請求 ID 能把訊息關聯起來。它不會讓副作用變安全、不會讓工作者停下來，也不會保護一條串流不被慢速消費者拖垮。

**類型：** 實作
**程式語言：** Python
**先修單元：** 階段 13 第 09 與 13 課
**時間：** 約 120 分鐘

## 學習目標

- 為 stdio 與 Streamable HTTP 各實作正確的取消訊號。
- 解決完成與取消的競態，而且不在取消之後還送訊息。
- 把請求取消跟持久的 `tasks/cancel` 語意分開。
- 依副作用與明確的幂等鍵來做重試決策。
- 替進度佇列設上限，同時保住最終回應。
- 透過重連、重新取回與帶抖動的退避來復原串流。

## 問題所在

順風路徑藏著最貴的那些分散式系統臭蟲。

客戶端呼叫一項工具。伺服器開始工作。進度傳來。一個代理把串流緩衝起來。客戶端到了逾時就斷線。伺服器在一毫秒之後完成。客戶端用一個新的 JSON-RPC id 重試。那個變更操作跑了兩次。

每個元件在本地都行為正常。整個系統在全局上失敗了。

MCP 定義了訊息與傳輸的行為，但你的應用程式仍然要負責：

- 時間預算；
- 業務層的幂等；
- 有上限的佇列；
- 重試分類；
- 持久的任務狀態；
- 重連與重新取回的政策。

這一課把那些決策做進一個決定性的模擬器裡。沒有 sleep、沒有 socket、沒有隨機失敗。取消事件的順序由你直接控制。有一個同步過的執行緒測試，會逼兩個帳本客戶端去搶同一個幂等鍵。

## 請求取消依傳輸而異

在每一種傳輸上意圖都一樣：客戶端不再需要那個進行中的結果。但線路上的訊號不同。

### stdio

stdio 用的是一條共用的雙向通道。客戶端送出一則通知：

```json
{
  "jsonrpc": "2.0",
  "method": "notifications/cancelled",
  "params": {
    "requestId": 41,
    "reason": "User closed the operation"
  }
}
```

這則通知是送出即忘。伺服器不會對它發出任何 JSON-RPC 回應。

伺服器應該停止工作、釋放資源，並避免替那個被取消的請求送出回應。當那個請求未知、已經結束，或沒辦法安全停下來時，它可以忽略取消。

格式不對、未知，以及已完成的取消通知都會被忽略。把那些競態變成新的錯誤，只會造出更多競態。

### Streamable HTTP

現代的 Streamable HTTP 給每一個請求自己的 HTTP 回應或 SSE 回應串流。客戶端取消的方式，是把那個請求的回應串流關掉。

不要為了一個普通的 HTTP 請求去 POST `notifications/cancelled`。串流關閉就是取消訊號。

一旦伺服器觀察到斷線，它就應該停止工作，而且不得再為那個請求送出任何訊息。

### 伺服器發起的取消範圍很窄

伺服器不會用 `notifications/cancelled` 去取消客戶端的任意呼叫。在 stdio 上，伺服器發起的取消只保留給終止一個 `subscriptions/listen` 請求。把那條路徑跟一般的客戶端請求取消分開。

## 取消是一場競態

兩種事件順序都是有效的。

### 取消勝出

```text
request starts
client sends cancellation signal
server marks request cancelled
worker reaches completion
server suppresses the response
```

### 完成勝出

```text
request starts
worker commits the result
server sends the response
cancellation arrives late
server ignores the late notification
```

客戶端也必須忽略一個它已經放棄的請求所收到的遲到回應。網路延遲意味著兩邊都證明不了對方先看到哪個事件。

```figure
mcp-reliability-race
```

這一課的 `RequestCoordinator` 只存一個終態。取消之後，`complete()` 不回傳任何回應。一個遲到的取消也改不了一筆已完成的紀錄。

## 逾時需要兩個時鐘

單一個閒置計時器不夠。

用兩道上限：

1. **閒置逾時。** 這個請求可以多久不產出任何有用的活動。
2. **最大逾時。** 從請求開始起算的絕對牆鐘預算。

進度可以重置閒置時鐘。它絕不能移除那個最大期限。

```text
start: 0 ms
progress: 400 ms
progress: 800 ms
progress: 1200 ms
idle timeout: 500 ms
maximum timeout: 2000 ms
```

在 1500 ms 時，這個請求還活著，因為最近一次進度只過了 300 ms。在 2000 ms 時，最大期限會把它取消，就算 1999 ms 又來了一個進度事件也一樣。

進度是選配的。伺服器可以接受一個進度 token，然後什麼更新都不發。絕不要把「有 token」變成無限逾時。

MCP 的進度值必須遞增。通知在完成或取消之後停止。替進度設速率限制，好讓一個很快的工作者沒辦法把傳輸淹掉。

## 請求取消不是 `tasks/cancel`

這兩套機制解的是不同的生命期。

| 機制 | 目標 | 訊號 | 成功代表什麼 |
|-----------|--------|--------|--------------------|
| stdio 上的請求取消 | 一個進行中的 RPC | `notifications/cancelled` | 客戶端放棄了這個請求；伺服器在可行時應該停下來 |
| HTTP 上的請求取消 | 一條進行中的回應串流 | 關掉那條串流 | 客戶端放棄了這個請求；伺服器在可行時應該停下來 |
| `tasks/cancel` | 一個持久的 Task | 一個普通的 MCP 請求 | 伺服器確認收到了取消意圖 |

一份成功的 `tasks/cancel` 結果，不能證明工作者停了。那個任務可能維持 `working`，直到某個工作者檢查點看到那個旗標。工作也可能在那個檢查點之前就完成了。

不要因為 HTTP 連線關掉就抹掉持久的任務狀態。之所以要建立一個 Task，就是因為它的生命週期活得比一個請求、一條連線更久。

## 一個新的 JSON-RPC ID 不是幂等

JSON-RPC 的 id 關聯的是請求與回應。它們並不標識一項業務操作。

假設客戶端用 id `41` 送出一筆扣款、丟了回應，然後用 id `42` 重試。伺服器看到的是兩則不同的訊息。少了應用程式層的鍵，它沒辦法知道它們代表同一次結帳。

幂等鍵標識的是業務意圖：

```json
{
  "name": "charge_account",
  "arguments": {
    "account": "acct-7",
    "cents": 1200,
    "idempotencyKey": "checkout-7"
  }
}
```

伺服器存下：

- 那個鍵；
- 操作引數的指紋；
- 已提交的結果。

同一個鍵、同樣的引數，回傳存起來的結果。同一個鍵、不同的引數，被拒絕。這能防止不小心重用的鍵去改動另一項業務操作。

### 帳本邊界必須是原子且持久的

這個順序是不安全的：

```text
check key
run mutation
store result
```

兩個工作者可以都看到鍵不存在，然後都跑了那個變更操作。在副作用之後、寫入之前崩掉，也會讓重試時出現同樣的曖昧。

這一課用一個以檔案為後端的 SQLite 帳本。`BEGIN IMMEDIATE` 把鍵檢查、模擬的業務副作用、執行計數器與存下的結果，序列化進同一筆交易。因此兩條獨立的帳本連線用同一個鍵競爭時，會看到一份已提交的結果與一次執行。把帳本關掉再開回來，那筆紀錄還在。

每一個回傳值都是從存下的 JSON 重建的。呼叫方永遠不會收到帳本持有的那個可變物件，所以改動一個回傳的字典不會弄壞後續的重播結果。

模擬器的業務副作用，是同一筆 SQLite 交易裡的收據與執行計數器。真實的付款、部署或外部 API 呼叫，不會因為你寫了一張本機表就變成原子的。生產環境需要一筆持久的共用資料庫交易、一個交易式 outbox，或一個會強制同一個幂等鍵的上游供應商。單靠一把行程鎖，保護不了多個副本，也撐不過一次重啟。

### 重試矩陣

在實作重試之前先把它分類。

| 類別 | 例子 | 重試規則 |
|------|---------|------------|
| 安全 | 沒有副作用的決定性讀取 | 在弄清楚失敗邊界之後，用一個新的 JSON-RPC id 重試 |
| 有條件 | 帶持久幂等鍵的變更操作 | 用同一個鍵與完全一樣的引數重試 |
| 不安全 | 沒有業務去重的變更操作 | 不要自動重試；先對帳 |

`readOnlyHint` 與 `idempotentHint` 這類工具註記，仍然是不可信的提示。重試安全性由應用程式契約與伺服器實作決定。

## 背壓是正確性的一部分

一個 SSE 生產者產生進度的速度，可能比客戶端、代理或網路消費得掉的還快。一個沒有上限的佇列，會把「慢」變成「記憶體耗盡」。

用一個有上限的佇列，並且定義什麼東西可以被丟掉。

進度是可替換的。對同一個 token，較晚的進度值會取代較早的。一份最終的 JSON-RPC 回應不可替換。

這一課的緩衝區套用這套政策：

1. 把同一個 token 的相鄰進度合併。
2. 到達容量上限時丟掉最舊的進度。
3. 把這條串流標記為需要向權威來源重新取回。
4. 保住那份最終回應。
5. 拒絕那種「為了保住一份最終回應就得丟掉另一份最終回應」的狀態。

這是有界的損失加上明確的復原。無聲的損失不是一種策略。

### 代理緩衝

伺服器可以正確地串流，而一個反向代理卻把事件壓在緩衝區裡。

對一份 SSE 回應，送出：

```http
Content-Type: text/event-stream
Cache-Control: no-cache
X-Accel-Buffering: no
```

2026 年的 Streamable HTTP 規格建議用 `X-Accel-Buffering: no`，好讓相容的代理立刻把事件送出去。

對安靜的長生命週期串流，週期性地送出一則 SSE 註解：

```text
:
```

客戶端會忽略註解行。中介看得到流量，就比較不會把一條閒置連線關掉。

保活不是進度。不要只因為一則傳輸註解到了，就把某個操作在語意上的閒置逾時重置。

## 重連就是重新取回

現代的 Streamable HTTP 不支援用 `Last-Event-ID` 做可續接的 SSE。

當一條 `subscriptions/listen` 串流掉線之後：

1. 用一個新的 JSON-RPC id 開一個新的 listen 請求。
2. 把想要的訂閱過濾條件還原。
3. 從權威方法重新取回受影響的工具、資源、提示詞或 Task。
4. 用穩定的識別碼替應用程式狀態去重。
5. 不要只因為某個不安全變更操作的回應丟了就把它重播一次。

範例的復原計畫明確把 `sendLastEventId` 設為 false，並列出要重新取回的資源。

### 防止重連風暴

如果一萬個客戶端在整整一秒時同時重連，那台正在復原的伺服器會再掛一次。

用帶抖動與上限的指數退避。這一課用客戶端 id 與嘗試次數算出決定性的抖動，好讓測試維持可重現：

```text
attempt 0: up to 250 ms
attempt 1: up to 500 ms
attempt 2: up to 1000 ms
...
cap: 8000 ms
```

生產環境可以用密碼學安全或執行環境的隨機性。不變的是那個分布，不是某一條特定公式。

## 動手實作

`code/main.py` 建了五個小型的可靠性元件。

### `RequestCoordinator`

- 帶著閒置與最大期限開始一個進行中的請求；
- 發出單調遞增的進度通知；
- 產生正確的 stdio 或 HTTP 取消訊號；
- 忽略無效的取消通知；
- 把取消與完成這兩種終態競態顯式化；
- 把伺服器發起的取消保留給 stdio 的訂閱。

### `MutationLedger`

- 證明少了業務鍵時，兩個 JSON-RPC id 會執行兩次；
- 用一筆以檔案為後端的 SQLite 交易，包住鍵檢查、模擬副作用、執行計數器與結果提交；
- 在獨立的帳本連線之間，對同一個幂等鍵下引數相符的請求做去重；
- 拒絕同一個鍵被拿去配不同的引數；
- 回傳防禦性副本，並在重新開啟之後保住已提交的紀錄。

### `DurableTaskService`

- 確認收到一個取消請求；
- 在工作者檢查點之前讓任務維持 `working`；
- 示範為什麼「確認收到」不等於最終狀態。

### `BoundedSseBuffer`

- 在壓力下合併或丟掉進度；
- 記下需要向權威來源重新取回；
- 從不丟掉那份最終回應。

### 復原輔助程式

- 回傳對代理安全的 SSE 標頭與保活註解；
- 建出一份重連與重新取回的計畫；
- 用決定性的指數退避與抖動把重試散開。

```bash

```

這支示範會把那場核心競態的兩邊都跑一次、在一個臨時的檔案後端帳本裡執行一次以交易去重的變更操作、把一個有上限的進度緩衝區灌爆，並展示一個持久的 Task 從「確認收到取消」走到「工作者觀察到取消」。

## 互動實驗

在不加任何 sleep 的情況下，跑四種事件順序。

1. 開始請求 `A`、取消它，然後呼叫 `complete()`。
2. 開始請求 `B`、把它完成，然後把取消送達。
3. 開始請求 `C`，在每一個閒置期限之前都發出進度，然後跨過最大期限。
4. 在 Streamable HTTP 上開始請求 `D`，然後把它的回應串流關掉。

每一種情境都記下：

- 請求的終態；
- 有沒有最終回應存在；
- 被放到線路上的取消訊號；
- 客戶端該忽略哪一個事件。

然後把 `D` 換成 stdio。操作一模一樣，但取消訊號必須改變。

## 練習實驗

替 `MutationLedger` 加上一個 `reserve_inventory` 變更操作。

要求：

1. 那個鍵綁定 SKU、數量、租戶與操作名稱。
2. 用同一個鍵與同樣引數重試，會回傳第一次的預留。
3. 改了數量的重試會失敗，而且不會多預留一次。
4. 一次已提交卻丟了回應的執行，可以靠鍵對帳。
5. 結果裡不記任何密鑰或付款資料。
6. 當客戶端沒有提供鍵時，關掉自動重試。
7. 加上一次模擬的訂閱掉線，並在決定下一步之前先重新取回那筆庫存紀錄。
8. 讓兩條帳本連線在一道屏障上一起出發，並行送出同一個鍵。斷言只有一次預留被提交。
9. 改動第一次回傳的那個預留物件。重播那個鍵，證明存下的結果沒有變。
10. 把帳本檔案關掉再開回來，然後用鍵去對帳那筆預留。

讓這個實驗保持誠實：如果庫存住在另一個服務裡，就說明那個服務會不會接受同一個幂等鍵，或者是否有一個交易式 outbox 把本機提交橋接到那個遠端副作用。

## 出貨產物

`outputs/skill-mcp-reliability-reviewer.md` 是一個扁平的可靠性審查技能。給它一項 MCP 操作、傳輸、逾時政策、重試行為、佇列政策與復原計畫。它會回傳一張競態表、重試分類、幂等邊界、流量控制檢查，以及失敗用的測試素材。

## 驗證成果

當下列敘述都成立時，這一課就完成了：

- stdio 的取消會送出 `notifications/cancelled`，而且收不到任何回應。
- Streamable HTTP 的取消會關掉那個請求的串流，而且不送任何取消 POST。
- 先取消後完成，會壓下那份最終回應。
- 先完成後取消，會保住回應，並忽略那個遲到的取消。
- 進度可以重置閒置逾時，但絕不會重置最大逾時。
- 光換一個新的 JSON-RPC id，那個變更操作就會再跑一次。
- 在兩條連線並行競爭下，同一個幂等鍵與完全一樣的引數只會執行一次。
- 一筆已提交的紀錄能撐過重新開啟，而重播回傳的是一份防禦性副本。
- 改動一份回傳的結果，改不了存下的結果。
- 有上限的緩衝區待在容量之內，並保住那份最終回應。
- 重連用的是一個新請求、不送 `Last-Event-ID`，並重新取回受影響的狀態。
- `tasks/cancel` 的確認收到，會讓那個任務在工作者看到它之前維持非終態。

## 生產環境的失敗模式

| 失敗 | 看得到的症狀 | 正確的回應 |
|---------|--------------------|------------------|
| HTTP 客戶端去 POST 取消通知 | 伺服器與客戶端對請求生命期的看法不一致 | 關掉那個請求的 SSE 回應串流 |
| 伺服器在接受取消之後還回應 | 客戶端收到一個沒用的遲到結果 | 取消勝出時就停止工作並壓下後續訊息 |
| 進度把每一個期限都重置 | 卡住的工作永遠活著 | 另外維持一個絕對的最大逾時 |
| 新的 RPC id 被當成去重 | 扣款、部署或刪除跑了兩次 | 加上一個持久的應用程式幂等鍵 |
| 鍵檢查與副作用是分開的 | 並行的工作者都看到鍵不存在 | 把鍵的宣告、副作用紀錄與結果原子地一起提交 |
| 跨副本使用記憶體內帳本 | 重啟或另一個工作者忘掉先前的提交 | 用共用的持久儲存，或上游的幂等 |
| 直接回傳存下的可變結果 | 呼叫方的改動弄壞後續重播 | 把已提交的結果序列化，並回傳防禦性副本 |
| 同一個鍵被拿去配不同引數 | 一個鍵替兩種業務意圖取了別名 | 存下並比較引數指紋 |
| 沒有上限的進度佇列 | 遇到慢速消費者時記憶體一路上升 | 在上限之內合併並丟掉可替換的進度 |
| 壓力下把最終回應丟掉 | 客戶端沒辦法知道請求的結果 | 保留容量或淘汰進度，絕不淘汰最終回應 |
| 代理緩衝 SSE | 進度成批到達，或在逾時之後才到 | 關掉緩衝，並設好相容的代理逾時 |
| 假設有 `Last-Event-ID` | 客戶端從伺服器不支援的狀態續接 | 用一個新請求重連並重新取回 |
| 每個客戶端都立刻重連 | 復原造出另一次停機 | 用帶上限與抖動的指數退避 |
| 把 Task 的確認收到當成取消已完成 | UI 說停了，工作者還在跑 | 一直輪詢那個 Task，直到終態 |

## 與總結專案的連結

工具生態系的總結專案應該把可靠性當成可執行的證據，不是架構圖裡的一段文字。

要求這些產物：

- 每一種傳輸各一份取消競態的逐字紀錄；
- 每一個暴露出去的變更操作各一張重試表；
- 一筆幂等鍵紀錄與一份引數不符的測試素材；
- 一份同鍵並行的逐字紀錄、一次重新開啟檢查，以及一次改動別名檢查；
- 一份有上限緩衝區被灌爆的結果；
- 反向代理的 SSE 標頭與閒置政策；
- 一份指名權威重新取回方法的重連計畫；
- 當總結專案用到 Task 時，一份持久 Task 取消的追蹤。

在一個本機行程裡跑出綠燈，只證明了順風路徑。當丟掉的回應、遲到的取消、慢速消費者與重連風暴都有決定性的結果時，這個總結專案才算生產就緒。

## 關鍵術語

| 術語 | 意思 |
|------|---------|
| 請求取消 | 放棄一個進行中的 MCP 請求 |
| 取消競態 | 終態完成與取消事件之間的競爭 |
| 閒置逾時 | 自上一次有用的請求活動起算的上限 |
| 最大逾時 | 從請求開始起算的絕對上限，不受進度影響 |
| 幂等鍵 | 替一項業務意圖去重的應用程式識別碼 |
| 原子帳本 | 把鍵的宣告、副作用紀錄與結果當成一個單位提交的持久邊界 |
| 背壓 | 當生產者快過消費者時所施加的控制 |
| 進度合併 | 用較新的權威值取代較舊的進度 |
| 重新取回 | 在串流出現缺口之後，再讀一次當前狀態 |
| 抖動 | 刻意加入的變化，把重試沿時間散開 |
