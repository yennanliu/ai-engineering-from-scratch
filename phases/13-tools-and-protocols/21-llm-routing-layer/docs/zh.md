# LLM 路由層 —— LiteLLM、OpenRouter、Portkey

> 被供應商鎖定的代價很貴。不同的工具呼叫工作負載，適合不同的模型。路由閘道給你單一的 API 表面、重試、故障轉移、成本追蹤與護欄。2026 年由三種原型主導：LiteLLM（開源自架）、OpenRouter（託管 SaaS）、Portkey（生產級，2026 年 3 月開源）。這一課會替那些決策準則命名，並走過一個 stdlib 的路由閘道。

**類型：** 學習
**程式語言：** Python (stdlib, routing + failover + cost tracker)
**先修單元：** 階段 13 · 02（函數呼叫）、階段 13 · 17（閘道）
**時間：** 約 45 分鐘

## 學習目標

- 分辨自架、託管與生產級三種路由選項。
- 實作一條退路鏈，在供應商失敗時依既定的優先順序重試。
- 跨供應商追蹤每次請求的成本與詞元用量。
- 針對給定的生產限制，在 LiteLLM、OpenRouter 與 Portkey 之間做選擇。

## 問題所在

供應商路由會派上用場的情境：

1. **成本。** Claude Sonnet 的價格是 Haiku 的 3 倍。做檢傷分類任務時 Haiku 就夠了；做合成任務時 Sonnet 才值得。要逐請求路由。

2. **故障轉移。** OpenAI 有個把小時很糟。每一次請求都失敗。你希望不必重新部署就能自動退到 Anthropic。

3. **延遲。** 即時聊天 UI 需要很快的首個詞元時間。批次摘要器則不需要。要依延遲 SLA 路由。

4. **法遵。** 歐盟使用者必須留在歐盟區域。要依區域路由。

5. **實驗。** 在同一份工作負載上 A/B 測兩個模型。要依測試桶路由。

每次整合都把這些手工寫一遍，很重複。路由閘道給你單一組相容 OpenAI 的 API，其餘的它來處理。

## 核心概念

### 相容 OpenAI 的代理形狀

大家說的都是 OpenAI 那套形狀。路由閘道暴露 `/v1/chat/completions`、接受 OpenAI 的 schema，並在內部代理到 Anthropic／Gemini／Cohere／Ollama／任何東西。客戶端不必在意。

### 模型別名

你的程式碼寫的不是釘死的快照 id，而是 `our_smart_model`。閘道負責把別名對映到真正的模型。當某家供應商出貨新世代時，你在伺服器端改那個別名；你的程式碼一個字都不用動。

### 退路鏈

```
primary: openai/gpt-4o
on 5xx: anthropic/claude-3-5-sonnet
on 5xx: google/gemini-1.5-pro
on 5xx: refuse
```

閘道在設定檔中定義這個。重試會計入一份預算，好讓退路的連鎖不會把成本炸開。

### 語意快取

一模一樣或近乎一模一樣的提示詞會打到快取，而不是打到供應商。在反覆執行的代理迴圈上，可以省下 30% 到 60%。鍵是基於嵌入的；近乎相同的提示詞共用同一個快取槽。

### 護欄

閘道層級的：

- **PII 遮蔽。** 在送出提示詞之前，跑一次正規表示式或機器學習的掃描。
- **政策違規。** 拒絕含有被禁內容的提示詞。
- **輸出過濾。** 清洗補全結果中的洩漏。

Portkey 與 Kong 都出貨了有主張的護欄。LiteLLM 則讓它們保持選配。

### 逐金鑰速率限制

一把 API 金鑰 = 一支團隊。逐金鑰的預算能防止某一支團隊把共享配額吃光。多數閘道都支援這個。

### 自架對託管的取捨

| 因素 | LiteLLM（自架） | OpenRouter（託管） | Portkey（生產級） |
|--------|----------------------|----------------------|----------------------|
| 程式碼 | 開源，Python | 託管 SaaS | 開源（2026 年 3 月）+ 託管 |
| 建置 | 部署一個代理 | 註冊 | 兩者皆可 |
| 供應商 | 100 家以上 | 300 家以上 | 100 家以上 |
| 計費 | 用你自己的金鑰 | OpenRouter 點數 | 用你自己的金鑰 |
| 可觀測性 | OpenTelemetry | 儀表板 | 完整 OTel + PII 遮蔽 |
| 最適合 | 想要完全掌控的團隊 | 快速做原型 | 有法遵需求的生產環境 |

當你有一支 SRE 團隊、又想要資料主權時，LiteLLM 勝出。當你想要單一份訂閱、不想管基礎設施時，OpenRouter 勝出。當你需要開箱即用的護欄與法遵時，Portkey 勝出。

### 成本追蹤

每一次請求都帶著 `provider`、`model`、`input_tokens`、`output_tokens`。乘上各模型的每詞元價格（從閘道維護的一份價目表中取得）。再依使用者／團隊／專案彙總。

### MCP 加上路由

一個閘道可以同時路由 LLM 呼叫「與」MCP 的 sampling 請求。當一次 sampling 請求的 modelPreferences 偏好某個特定模型時，閘道就轉譯到正確的後端。這也是階段 13 · 17（MCP 閘道）與本課的路由閘道，有時會合併成同一個服務的地方。

### 路由策略

- **靜態優先權。** 用清單中的第一個；出錯就退到下一個。
- **負載平衡。** 輪詢或加權。
- **成本感知。** 挑出滿足延遲／品質要求中最便宜的模型。
- **延遲感知。** 挑出過去 N 分鐘內最快的模型。
- **任務感知。** 由一個提示詞分類器把寫程式導向某個模型、把摘要導向另一個。

## 框架應用

`code/main.py` 用約 150 行實作了一個路由閘道：接受 OpenAI 形狀的請求、轉譯成各供應商的樁、跑一條優先權退路鏈、追蹤每次請求的成本，並對輸入跑一次 PII 遮蔽。用三種情境跑跑看：正常請求、主要供應商故障而觸發退路、被遮蔽攔下的 PII 外洩。

要看的地方有：

- `ROUTES` dict：別名 -> 依優先權排序的具體供應商清單。
- 退路迴圈在 5xx 時重試。
- 成本追蹤器把詞元用量乘上各模型的費率。
- PII 遮蔽器在轉發之前清掉 SSN 形狀的樣態。

## 產出交付

這一課產出 `outputs/skill-routing-config-designer.md`。給定一份工作負載輪廓（延遲、成本、法遵），這項技能會在 LiteLLM／OpenRouter／Portkey 之間做出選擇，並產出一份路由設定。

## 練習

1. 跑一次 `code/main.py`。觸發那個故障情境；確認退路落在第二家供應商上，而且成本被正確歸屬。

2. 加上語意快取：以提示詞的 SHA256 當查找鍵；命中快取就立刻回傳。在一次重複呼叫上量測省下的成本。

3. 加上一個提示詞分類器，把「code ...」開頭的提示詞導向偏好智能的別名，把「summarize ...」開頭的導向偏好速度的別名。

4. 設計逐團隊的預算：每支團隊有一個月度支出上限；一旦到頂，閘道就拒絕請求。挑一個強制執行的粒度（逐請求或依時間窗）。

5. 把 LiteLLM、OpenRouter 與 Portkey 的文件並排讀一遍。各說出一項它有、而另外兩家沒有的功能。

## 關鍵術語

| 術語 | 大家怎麼說 | 實際上是什麼 |
|------|----------------|------------------------|
| 路由閘道 | 「LLM 代理」 | 擺在眾多供應商前面、提供單一 API 表面的那一層 |
| 相容 OpenAI | 「說 OpenAI 那套 schema」 | 接受 `/v1/chat/completions` 形狀，並轉譯到任何後端 |
| 模型別名 | 「our_smart_model」 | 你程式碼裡的名字，由閘道對映到某個具體模型 |
| 退路鏈 | 「重試清單」 | 失敗時依序嘗試的供應商清單 |
| 語意快取 | 「提示詞嵌入快取」 | 鍵是提示詞的嵌入；近乎重複者共用同一次快取命中 |
| 護欄 | 「輸入／輸出過濾器」 | 遮蔽 PII、拒絕政策違規 |
| 逐金鑰速率限制 | 「團隊預算」 | 以一把 API 金鑰為範圍的配額 |
| 成本追蹤 | 「逐請求的花費」 | 詞元用量彙總乘上各模型的單價 |
| LiteLLM | 「那個開放代理」 | 可自架的開源路由閘道 |
| OpenRouter | 「那個託管 SaaS」 | 以點數計費的託管閘道 |
| Portkey | 「那個生產級選項」 | 開源 + 託管，內建護欄 |
