# 技能發現與漸進揭露

> 一項技能在它的本體被載入之前就已經有用了。它的名稱與描述替它在目錄裡爭到一個位置；它更深的那些檔案，只有在任務走到那裡時才爭到上下文。

**類型：** 實作
**程式語言：** Python (stdlib)
**先修單元：** 階段 13 · 22（代理技能：可攜的契約與執行環境邊界）
**時間：** 約 105 分鐘

## 學習目標

- 做出一條檔案系統發現流水線，把範圍、驗證、衝突政策與目錄發布分開。
- 說明三個揭露層級：目錄中繼資料、已啟用的指示，以及任務專屬的資源。
- 設計參考資料，讓代理能直接拿到需要的細節，而不必載入整個套件。
- 把目錄空間的預算跟已啟用技能的上下文預算分開估算。
- 當一項技能讀取它自己的資源時，擋掉路徑穿越與符號連結逃逸。

## 問題所在

你的代理裝了 200 個技能。在工作階段一開始就載入每一份 `SKILL.md`、參考檔案、腳本與樣板，會把當下的任務埋在一堆不相關的程序底下。什麼都不載入，又會逼使用者去記確切的檔案系統路徑。

常見的折衷是一份目錄：先給模型看每個合格技能的精簡身分與路由描述，等選定之後才載入完整本體。這帶來兩個新的工程問題。

第一，發現不只是遞迴搜檔。技能可以存在於專案、使用者、管理者、外掛或內建這幾種範圍。兩個套件可以同名。一條符號連結可以指到受信任根目錄之外。一個格式不對的套件可以吃掉目錄空間，或變成根本叫不動。

第二，漸進揭露可能變成漸進混亂。如果 `SKILL.md` 說「讀相關的那份指南」，而套件裡有十二份指南，模型只能猜。如果每份指南又各指向三份檔案，載入就變成一次沒有邊界的圖遍歷。

一個好的執行環境會讓發現變成確定的，讓揭露變成有意的。

## 核心概念

### 發現是一條編譯器流水線

把檔案系統當成原始碼輸入。不要把原始路徑直接發布給模型。

```figure
skill-discovery-pipeline
```

每一個階段都應該產出有結構的資料與有結構的失敗。一份發現日誌應該回答：

- 搜了哪些根目錄？
- 找到哪些候選？
- 哪些候選被擋掉，為什麼？
- 哪個套件贏了衝突？
- 哪些目錄項目因為預算而被縮短或被略去？

少了那些證據，「模型沒有用我的技能」幾乎沒辦法診斷。

### 範圍是執行環境的政策

可攜的規格定義的是一個技能套件，不是某一條通用的安裝路徑或優先順序。要搜哪裡，由宿主決定。

一個通用的執行環境可能會用這些範圍：

| 範圍 | 根目錄範例 | 預期的所有權 |
|---|---|---|
| 工作區 | `<repo>/.agents/skills/` | 專案維護者 |
| 使用者 | `<user-data>/skills/` | 單一位開發者 |
| 管理者 | `<system>/skills/` | 機器或組織政策 |
| 外掛 | 一份已簽署的外掛套組 | 外掛發布者與安裝程式 |
| 內建 | 執行環境套件 | 執行環境供應商 |

到 2026 年 8 月為止，Codex 記載的專案發現方式是從 `$CWD/.agents/skills` 沿祖先目錄一路往上到儲存庫根目錄，再加上使用者、管理者與內建位置。它支援以符號連結建立的技能目錄。同名的兩份可能都會出現，而不是被合併。那些是 Codex 的行為，不是 `SKILL.md` 的要求；在寫轉接器時，請去確認當時的 [Codex skill documentation](https://learn.chatgpt.com/docs/build-skills)。

絕不要從目錄名稱憑空發明優先順序。把它宣告成政策，然後測試它。這一課的實驗替每一個 `Scope` 都給了一個明確的整數排名，所以同一組候選永遠解出同一個結果。

### 衝突需要 `name` 之外的身分

兩個都叫 `release-readiness` 的套件可以都是合理的。其中一個可能是工作區的覆寫，另一個是使用者的預設。因此一筆目錄項目至少需要：

```json
{
  "name": "release-readiness",
  "description": "Inspect a release candidate for this repository.",
  "scope": "workspace",
  "source": "/repo/.agents/skills/release-readiness",
  "selected": true
}
```

常見的衝突政策包括：

| 政策 | 好處 | 風險 |
|---|---|---|
| 保留每一個候選 | 什麼都不會被藏起來 | 模型會看到有歧義的名稱 |
| 優先順序最高的範圍勝出 | 叫用很單純 | 一個本地套件可以遮蔽一個受信任的套件 |
| 拒絕重複 | 不會有無聲的遮蔽 | 合理的覆寫會失效 |
| 用來源限定名稱 | 身分明確 | 面向使用者的名稱會變長 |

替宿主選定一種政策。即使被拒絕或被遮蔽的候選不會出現在模型的目錄裡，也要把它們保留在診斷資訊中。

### 三個揭露層級

Agent Skills 規格描述的是分階段的載入。關鍵在於每一層有不同的目的。

```figure
skill-disclosure-levels
```

#### 層級 1：目錄中繼資料

模型需要足夠的資訊，才能把這項技能跟它的鄰居分開。規格估算每筆目錄項目大約 100 個 token，但實際的序列化與 token 化屬於宿主的事。

一段有用的描述有兩個子句：

```yaml
description: Validate a release candidate and produce a readiness report. Use when the user asks whether a version, tag, or package is ready to publish.
```

第一個子句說出能力。第二個子句說出觸發邊界。第 25 課會用正例與差一點的提示詞來評估這道邊界。

#### 層級 2：已啟用的指示

啟用之後，本體應該同時充當一張地圖與一套程序。規格建議把 `SKILL.md` 控制在 500 行以下。那是一個設計訊號，不是一個要填滿的目標。

本體應該包含：

- 任務邊界；
- 預設流程；
- 分支條件；
- 指向更深檔案的直接參考；
- 工具與腳本契約；
- 失敗與停止的行為；
- 預期的輸出以及它的驗證方式。

不要只為了讓進入檔變短，就把核心流程搬進參考資料。啟用時必須給模型足夠的上下文，讓它一開始就走對。

#### 層級 3：支援資源

參考資料提供的是文字或資料。腳本提供的是決定性的計算。素材是被複製、被填寫或被轉換成交付物的東西，不是被當成指示看的。

| 目錄 | 模型會讀它嗎？ | 模型會執行它嗎？ | 典型內容 |
|---|:---:|:---:|---|
| `references/` | 需要時會 | 不會 | schema、政策、領域指南 |
| `scripts/` | 可能會檢視 | 透過一個被允許的工具 | 驗證器、轉換器、收集器 |
| `assets/` | 只有在有用時 | 不會 | 樣板、測試素材、圖片、起始檔案 |

這些名稱是慣例，不是有魔法的能力。宿主仍然需要檔案存取權與一個執行工具。

### 依分支給的參考勝過主題大雜燴

把進入檔寫成一張決策地圖：

```markdown
## Choose the path

- For a Python package, read `references/python-release.md`.
- For a container image, read `references/container-release.md`.
- For a documentation-only release, read `references/docs-release.md`.
- If the release combines artifact types, read only the guides for those artifacts.
```

這讓每一份參考資料都有一個看得見的載入條件。「更多內容請讀 `references/`」沒有。

讓參考資料的圖保持淺。官方指引建議從 `SKILL.md` 直接連過去，並避免長鏈。只跳一次讓可達性可以被測試，也降低某個必要的限制條件永遠進不了上下文的機率。

```figure
skill-reference-map
```

### 目錄預算與已啟用的上下文是兩份不同的預算

令 `c_i` 是技能 `i` 序列化後的目錄成本、`B_c` 是目錄預算、`b_j` 是已啟用本體的成本，`r_k` 是真正被載入的資源。

```text
catalog_cost = sum(c_i for every published skill)
active_cost = sum(b_j for every activated skill) + sum(r_k for every disclosed resource)
```

砍掉其中一份預算，不會自動砍掉另一份。短描述可以省下目錄空間，但一份被啟用的 900 行本體照樣會把任務壓垮。把本體拆成參考資料，只有在執行環境與指示真的避開了不相關分支的載入時，才會降低已啟用的成本。

Codex 目前在知道上下文窗大小時，把初始技能清單的預算定為上下文窗的 2%。那個 8,000 字元的數值只是在不知道大小時的退路；它不是跟 2% 規則並用的第二道上限。當目錄超過適用的預算時，描述可能被縮短或略去。把那些數字當成 Codex 現行的政策，不是 Agent Skills 標準的性質。

### 資源路徑是一道信任邊界

一項技能應該只讀它套件裡的檔案。單純比對字串前綴是不夠的：

```text
references/../../../../.ssh/config
references/external-link -> /private/company-secrets
```

用檔案系統的語意去解析套件根目錄與候選路徑、拒絕絕對路徑輸入，並確認解析後的候選仍然落在解析後的根目錄底下。在發現之前就決定符號連結准不准。如果准，每一次都要檢查解析後的目標。

```figure
skill-resource-containment
```

路徑被關住不等於內容可信。一份有效的套件內參考資料照樣可以裝著惡意指示。第 26 課處理那個威脅。

### 載入必須是看得見的

在不記錄密鑰的前提下記下揭露事件：

```json
{
  "event": "skill.resource.loaded",
  "skill": "release-readiness",
  "resource": "references/python-release.md",
  "reason": "candidate contains pyproject.toml",
  "bytes": 2840
}
```

那個 reason 把一次上下文的選擇變成可被審查的證據。它也幫得上忙，讓你找出那些會讓代理「以防萬一」把每個檔案都載進來的指示。

## 動手實作

`code/main.py` 建了一個決定性的發現與揭露引擎。

發現這一側包含：

- `Scope`，承載來源與優先順序中繼資料；
- `SkillCandidate`，代表一個尚未驗證的檔案系統候選；
- `discover_scope(scope)`，列舉直屬的技能目錄；
- `resolve_collisions(candidates, precedence)`，套用一條宣告好的政策；
- `CatalogEntry` 與 `build_catalog(...)`，發布有上限的中繼資料；
- `CatalogBudget`，替序列化後的項目記帳，同時不假裝字元就等於通用的 token。

揭露這一側包含：

- `load_skill_body(entry, ...)`，處理層級 2 的啟用；
- `validate_reference(skill_dir, reference)`，做路徑關住的檢查；
- `load_reference(...)`，做有上限的層級 3 讀取。

跑這個實驗：

```bash
cd "$(git rev-parse --show-toplevel)"
cd phases/13-tools-and-protocols/24-skill-discovery-and-progressive-disclosure
python3 code/main.py
python3 -m unittest discover -s code/tests -v
```

這段指令需要一份本機 clone，而且會從那份 clone 裡的任何工作目錄解析出儲存庫根目錄。

這支示範會建立臨時的專案範圍與使用者範圍、塞進一次衝突、在一個刻意壓小的預算下建出目錄、啟用一項技能，然後同時嘗試一次合法的參考讀取與一次穿越逃逸。它不會安裝任何永久檔案。

### 為什麼發現是淺的

`discover_scope` 只檢查直屬子目錄裡有沒有 `SKILL.md`。它不會把每一份嵌套的 `SKILL.md` 都遞迴當成獨立套件。這保住了套件邊界，也避免把一個已安裝技能裡的範例或測試素材不小心發布出去。

### 為什麼這個實驗不解析任意 YAML

這個實驗只支援它的目錄所需要的純量 frontmatter。生產環境的執行環境應該用一個安全的 YAML 解析器，配上明確的 schema、大小上限，並關掉自訂物件的建構。「只用標準庫」是一個教學上的限制，不是默默發明一套殘缺 YAML 方言的許可。

## 框架應用

把這份檢查清單套到任何發現轉接器上：

1. 列出每一個設定好的根目錄，以及誰可以寫入它。
2. 說明以符號連結建立的套件准不准。
3. 驗證套件名稱、目錄名稱、必要中繼資料，以及進入檔本體的大小。
4. 在內部身分裡保住來源與範圍。
5. 宣告並測試同名時的行為。
6. 量測真正送給模型的那份序列化目錄。
7. 記下某份本體或資源為什麼被載入。
8. 讓資源讀取留在解析後的套件根目錄裡。
9. 被參考的檔案不存在時，要明確地失敗。
10. 當安裝或政策改變時重建目錄。

## 產出交付

本單元會產出 `skill-catalog-builder` 套組。它會掃描明確排好序的根目錄、擋掉以符號連結建立的進入檔與名稱／目錄不符、解決跨範圍的衝突、拒絕同優先順序的重複，並把選中的中繼資料塞進宣告好的項目數、描述長度與序列化字元預算裡。

它的 JSON 報告裡有選中的項目、被遮蔽的候選、被略去的項目、驗證錯誤、優先順序與預算使用量。本體與參考資料的載入仍然是分開的執行期操作，所以這個目錄建構器不會執行腳本，也不會把整個套件放進上下文。

## 練習

1. 加上一個外掛範圍，並把它的優先順序排在使用者與內建之間。用一個測試證明衝突的結果。
2. 把衝突政策從「優先順序最高者勝」改成「限定名稱」。讓兩筆項目都留在目錄裡。
3. 替 `load_reference` 加上位元組大小上限。測試一個剛好在上限上的檔案，以及一個超過一個位元組的檔案。
4. 寫兩段聽起來幾乎一樣的描述。把它們改寫到觸發邊界不再重疊。
5. 加上一份清單，裡面裝著每一份參考資料與腳本的雜湊。在載入之前就偵測出被改過的資源。
6. 替這支示範加上量測，分別回報層級 1、層級 2 與層級 3 的位元組數。

## 關鍵術語

| 術語 | 大家怎麼說 | 實際上是什麼 |
|---|---|---|
| 技能發現 | 「把每一份 SKILL.md 找出來」 | 搜尋設定好的範圍、驗證套件、附上來源出處，並套用政策 |
| 技能目錄 | 「已安裝技能的清單」 | 給合格套件用的、模型看得見的精簡路由中繼資料 |
| 衝突政策 | 「重複的時候誰贏」 | 一條宣告好的規則，處理來自不同來源的同名候選 |
| 漸進揭露 | 「延遲載入」 | 從目錄到本體再到分支專屬資源的分階段上下文准入 |
| 參考圖 | 「技能連到的那些檔案」 | 可達的資源結構，以及它們的載入條件 |
| 路徑關住 | 「留在那個資料夾裡」 | 確認解析後的資源目標仍然在解析後的套件根目錄之內 |
