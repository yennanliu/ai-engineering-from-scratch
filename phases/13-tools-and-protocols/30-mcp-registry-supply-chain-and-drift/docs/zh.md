# MCP 登錄庫供應鏈：准入、漂移與回滾

> 一筆登錄庫項目告訴你的是某個發布者宣告了什麼。生產環境的准入要證明的是你取到了什麼、觀察到了什麼、核可了什麼，以及你能安全還原成什麼。

**類型：** 實作
**程式語言：** Python
**先修單元：** 階段 13 · 17（閘道與登錄庫）、階段 13 · 18（生產環境的認證）
**時間：** 約 90 分鐘

## 學習目標

- 把登錄庫發布、套件來源出處、執行期發現與本地核可分開。
- 在不信任紀錄裡自報名稱的前提下，驗證一台 MCP 伺服器的命名空間。
- 釘住不可變的發布、執行來源、來源出處與即時描述子這幾類證據。
- 在准入之後偵測登錄庫狀態變化與執行期漂移。
- 在不改寫歷史的前提下，把路由回滾到一個先前被准入的版本。
- 維護一份可察覺篡改的准入帳本，替每一個決策說明理由。

## 問題所在

你在某個登錄庫裡找到 `com.example/inventory`。它的描述看起來沒問題。它的套件存在。那台伺服器回應 `server/discover`。

那不是一個事實。那是一條來自不同權威的事實鏈：

1. 一個針對某命名空間完成認證的發布者提交了一筆紀錄。
2. 一個套件登錄提供了一份具備特定身分與摘要的產物。
3. 一個正在執行的端點回報了一個協定版本、能力、工具，以及診斷用的伺服器資訊。
4. 你的組織決定這個確切的組合是被允許的。

把那些事實壓成「它在登錄庫裡，所以可以信」，會造出一個供應鏈盲點。一筆有效的發布照樣可以被棄用。如果你沒有釘住摘要，一個套件標籤可能指到一份沒預期到的產物。一台伺服器可以在審查之後才加上一項破壞性工具。一次回滾可能默默選到一個從來沒被准入過的版本。

解法是一個在每一道邊界上都有證據的准入控制器。

## 登錄庫是索引，不是你的核可系統

官方 MCP 登錄庫存的是伺服器中繼資料。它的 `server.json` 紀錄指名一個伺服器版本，並宣告一個或多個套件或遠端端點。發布規則再加上命名空間認證、套件所有權檢查、受限登錄的規則，以及一個很窄的發布者中繼資料位置。

那些控制回答的是發布問題。你的生產政策仍然要回答部署問題：

| 邊界 | 它問的問題 | 證據的所有者 |
|---|---|---|
| 命名空間 | 這個發布者被允許用這個名稱嗎？ | 登錄庫認證，加上你自己驗過的命名空間輸入 |
| 紀錄 | 發布者替這個版本宣告了什麼？ | 不可變的 `server.json` 摘要 |
| 執行來源 | 到底哪個套件或遠端端點會被執行？ | 宣告的來源欄位、已驗證的所有權結果、傳輸，以及可信的摘要 |
| 執行期 | 這個端點現在暴露了什麼？ | `server/discover` 與工具描述子 |
| 准入 | 你的政策核可了這個確切的集合嗎？ | 本地的釘選與帳本項目 |
| 維運 | 它還安全嗎，而且有什麼能取代它？ | 漂移檢查、狀態同步、健康狀態，以及回滾路由 |

登錄庫的 schema 版本與 MCP 協定版本互相獨立。一筆紀錄可以用已發布的 `2025-12-11` 伺服器 schema，而活著的伺服器支援 MCP `2026-07-28`。絕不要從其中一個推論另一個。

```figure
mcp-registry-admission
```

## 一次准入決策裡的七道控制

### 1. 命名空間驗證

官方登錄庫的名稱使用經過認證的命名空間。一個驗過的網域可以映射到一個反轉的網域前綴。舉例來說，掌控 `example.com` 可以確立 `com.example/*`。

不要接受字串前綴檢查：

```python
server_name.startswith("com.example")
```

那也會接受 `com.exampleevil/tool`。要在 `/` 處把名稱切開、要求 slug 非空，並精確比對那個命名空間片段。更重要的是，要把驗過的命名空間從認證結果傳進准入。不要從那筆不可信的紀錄裡導出信任。

以 GitHub 為後盾的命名空間跟以網域為後盾的命名空間，走的是不同的認證路徑。把兩條路徑都正規化成同一個准入輸入：那個確切的、已驗證的命名空間字串。

### 2. 來源出處的接合

對一筆套件紀錄，宣告與取回的產物必須在明確的欄位上接得起來：

- 套件登錄的類型
- 套件識別碼
- 套件版本
- 已驗證的所有權結果
- 下載下來的產物摘要

也要驗證宣告的套件傳輸。一筆只有遠端端點的紀錄是有效的，不能因為它沒有套件就被拒絕。對一個遠端來源，要把宣告的網址與傳輸類型，接到獨立驗證過的端點所有權，以及那條受信任連線或部署證據的摘要上。

這一課的程式碼支援兩種來源，並把選定的來源跟登錄庫來源、伺服器名稱、登錄庫版本、紀錄摘要與證據摘要一起取雜湊。得出的來源出處摘要，是指向那整組證據的一個精簡指標。它不是保留證據的替代品。

絕不要接受一份只由你正想驗證的那個產物自己提供的摘要。在一個受信任的取回邊界上把它算出來，或從一個你會驗證其驗證結果的套件服務那裡拿到它。

### 3. 要釘住的是決策，不只是版本

登錄庫的版本是唯一的發布識別碼。已發布的中繼資料是不可變的。紀錄改了就要一個新版本。語意化版號是建議做法，但登錄庫並不要求它，也不接受版本範圍。

這意味著 `^1.4` 不是一個准入釘選。「latest」也不是。一個有用的釘選包含：

```json
{
  "server": "com.example/inventory",
  "version": "1.0.0",
  "recordDigest": "...",
  "source": {"kind": "package", "registryType": "pypi"},
  "sourceDigest": "...",
  "toolsetDigest": "...",
  "provenanceDigest": "...",
  "registryStatus": "active"
}
```

釘住好幾層，你才能指出是哪一道邊界變了。同一個登錄庫版本下紀錄摘要變了，是登錄庫的完整性失敗。同一個套件座標或遠端部署下來源摘要變了，是執行來源的完整性失敗。工具集摘要變了，是執行期漂移。

### 4. 即時的漂移偵測

准入應該去觀察那台真的會收到流量的伺服器。呼叫 `server/discover`，透過你受信任的路徑列出或以其他方式取得被暴露的工具描述子，並驗證：

- `supportedVersions` 裡有 `2026-07-28`
- 本地要求的所有能力都在
- 每一份工具描述子都有必要的身分與 schema 面
- 在後續檢查時，正規化後的描述子摘要跟被准入的釘選相符

選配結果 `_meta["io.modelcontextprotocol/serverInfo"]` 的值是自報的顯示、日誌與除錯脈絡。把它記成診斷證據，但絕不要用它來確立命名空間、套件所有權、端點所有權、准入，或任何其他安全決策。一個位在 `_meta` 之外、直接叫 `serverInfo` 的別名不是那個契約欄位，也不該被升級成診斷證據。

只正規化那些順序沒有意義的欄位。範例在取雜湊之前，先依穩定的名稱把工具清單排序，所以一次無害的清單順序變動不會造成漂移。它不會丟掉描述子欄位。新增一項工具、改掉 schema、改掉描述，或加上新的註記，都會改變釘選。

範例把格式不對的描述子，以及任何描述子摘要的變動都當成漂移，於是把釘選隔離、移除它的有效路由，並封鎖那個版本作為回滾目標。生產政策可以規定：即使只是文案上的改動，也只能透過一次新的審查才放行，因為描述會影響模型的工具選擇。「純外觀」的中繼資料照樣能改變代理的行為。

### 5. 登錄庫狀態是即時狀態

登錄庫 API 會在每一筆伺服器紀錄旁邊附上一個回應層級的 `_meta` 物件。由登錄庫管理的欄位住在 `_meta["io.modelcontextprotocol.registry/official"]` 底下。把回應的 `_meta` 物件傳進准入，並讀 `_meta["io.modelcontextprotocol.registry/official"].status`。直接的 `_meta.status` 值不是官方的線路形狀。也不要把回應中繼資料跟那筆發布紀錄自己的 `_meta` 搞混。狀態可以是：

- `active`：預設會回傳，而且有資格接受本地准入
- `deprecated`：仍然發現得到，但帶著警告，不再是一個安全的自動選項
- `deleted`：預設被隱藏，而它的歷史紀錄仍可透過 deleted 或增量視圖取得

在准入之後同步狀態。如果一個 active 的版本變成 deprecated 或 deleted，就把它的釘選隔離，並停止把新工作路由過去。證據留著。從預設清單裡被刪掉，不等於你可以抹掉自己的稽核軌跡。

發布者提供的自訂中繼資料，在發布紀錄裡只能放在 `_meta.io.modelcontextprotocol.registry/publisher-provided` 底下。登錄庫管理的回應中繼資料是分開的。不要讓發布者自己設定它的官方狀態。

### 6. 回滾是路由的還原

一筆不可變的發布不會在回滾時被編輯。回滾選的是一個先前被准入、目前仍合格的釘選，然後改變有效路由。

一個安全的目標必須：

1. 有一筆完成的准入紀錄。
2. 在你的政策之下仍然是 active 的登錄庫狀態。
3. 沒有被執行期或安全證據隔離。
4. 仍然解析到那個被釘住的套件與那組即時描述子。
5. 通得過當前的健康檢查。

範例聚焦在前三個條件。一個真正的調和器應該在啟用之前，重新取回套件並重新檢查那個活著的端點。

### 7. 追加一份准入帳本

一個准入資料庫說的是「現在什麼是有效的」。一份帳本說的是「為什麼」。

範例裡的每一筆項目包含一個序號、時間、事件、伺服器、版本、結果、理由、證據、前一筆項目的雜湊，以及它自己的雜湊。改掉一筆較舊的結果，會讓那筆項目與之後每一個連結的驗證都失敗。

這是可察覺篡改，不是有魔法的不可篡改。要把帳本頭週期性地錨定在另一個信任域裡，例如已簽署的發布中繼資料或一次寫入的儲存。限制誰可以追加。把授權權杖、套件憑證、工具引數與私有端點資料留在證據之外。

## 動手實作

那個可執行的控制器在 `code/main.py`。它只用 Python 標準庫。

先從那個有限的示範開始：

```bash
cd phases/13-tools-and-protocols/30-mcp-registry-supply-chain-and-drift
python3 code/main.py
```

這個示範做五件事：

1. 在命名空間、套件來源出處、協定、能力與工具都相符的情況下准入 `1.0.0`。
2. 准入 `1.1.0` 並讓它成為有效版本。
3. 在執行期觀察到一項沒預期到的刪除工具。
4. 觀察到 `1.1.0` 的登錄庫狀態變成 `deprecated`。
5. 把路由還原到仍被准入的 `1.0.0` 釘選。

預期的形狀：

```json
{
  "admitted": [true, true],
  "driftAllowed": false,
  "rollbackAllowed": true,
  "activeVersion": "1.0.0",
  "ledgerValid": true
}
```

依這個順序讀那份實作：

1. `namespace_for_domain()` 與 `namespace_matches()` 確立精確的命名權威。
2. `digest()` 與 `normalized_tools()` 產出決定性的證據。
3. `RegistryAdmissionController.admit()` 把發布、來源出處、執行期與政策接起來。
4. `check_live()` 把一次新的觀察跟釘選做比較。
5. `observe_registry_status()` 把登錄庫狀態變動的版本隔離。
6. `rollback()` 只啟用一個先前被准入且合格的目標。
7. `AdmissionLedger.verify()` 偵測出被記錄歷史的變動。

## 框架應用

把這個控制器擺在發現與路由之間：

```text
Registry sync -> artifact verifier -> live discovery -> admission controller -> route table
                                               |                 |
                                               v                 v
                                          evidence store    admission ledger
```

這些工作要用不同的身分。一個登錄庫同步工作者需要中繼資料的讀取權。一個產物驗證器需要套件取回權。一個路由調和器需要啟用一個已核可釘選的權限。它們沒有一個需要全部憑證。

把推出狀態顯式化。「已核可」是指證據通過了政策。「有效」是指路由目前選的是它。「已隔離」是指它不能接收新工作。「已被取代」是指另一個被准入的版本正在生效。不要把這四個意思編碼進同一個布林值。

在把一台伺服器暴露進 `tools/list` 之前先跑准入。否則客戶端就能在發布與政策評估之間那段空隙裡發現一項工具。

## 互動實驗

你會一次看一道邊界失敗。

### 實驗 A：命名空間碰撞

從程式碼目錄開一個 Python shell：

```bash
cd phases/13-tools-and-protocols/30-mcp-registry-supply-chain-and-drift/code
python3 -q
```

然後執行：

```python
from main import namespace_matches
namespace_matches("com.example/inventory", "com.example")
namespace_matches("com.exampleevil/inventory", "com.example")
```

第一個結果是 `True`；第二個是 `False`。在本機把那個精確比對換成 `startswith`，觀察為什麼第二個名稱跨過了邊界。繼續往下之前，把精確比對改回來。

### 實驗 B：描述子漂移

```python
from main import *
times = iter(f"2026-08-21T12:00:{n:02d}+00:00" for n in range(10))
c = RegistryAdmissionController(clock=lambda: next(times))
meta = {OFFICIAL_META_KEY: {"status": "active"}}
c.admit(sample_record("1.0.0"), meta, "com.example", evidence_for("1.0.0"), sample_live("1.0.0"))
c.check_live("com.example/inventory", "1.0.0", sample_live("1.0.0", True))
```

看那些理由與路由狀態。套件與登錄庫紀錄都沒變。變的是執行期的工具介面，所以控制器把釘選隔離並停用。這正是為什麼供應鏈控制必須在安裝之後繼續下去。

### 實驗 C：狀態與回滾

准入 `1.1.0`、把它標成 deprecated，然後兩個回滾目標都試一次：

```python
c.admit(sample_record("1.1.0"), meta, "com.example", evidence_for("1.1.0"), sample_live("1.1.0"))
c.observe_registry_status("com.example/inventory", "1.1.0", "deprecated")
c.rollback("com.example/inventory", "1.1.0", "unsafe retry")
c.rollback("com.example/inventory", "1.0.0", "restore known release")
c.ledger.verify()
```

被隔離的目標被拒絕。較早那個曾經有效的釘選被接受。帳本仍然有效。

## 練習實驗

替這個控制器加上一道兩人核可閘門。

要求：

- 把核可存成已簽署的證據參照，不要在釘選裡存可變的名字。
- 對含有 `destructiveHint: true` 工具的工具集，要求兩個不同的審查者身分。
- 拒絕重複的審查者身分。
- 當核可還不完整時，把原本那次准入嘗試保留在帳本裡。
- 為零個、一個、重複，以及兩個不同核可各加測試。
- 不要記下簽章、憑證或完整的私有工具引數。

成功的意思是：在兩個身分都核可了那個確切的紀錄、套件與工具集摘要之前，一項破壞性工具沒辦法生效。

## 驗證成果

跑那個示範與那組決定性的測試：

```bash
cd phases/13-tools-and-protocols/30-mcp-registry-supply-chain-and-drift
python3 code/main.py
python3 -m unittest discover -s code/tests -v
```

驗證應該證明：

- 精確的命名空間邊界會拒絕長得很像的前綴
- 只有那個官方具命名空間的登錄庫狀態，才能讓一個版本變得合格
- 未驗證或對不上的套件與遠端證據會被拒絕
- 發布者中繼資料沒辦法假冒登錄庫管理的中繼資料
- 工具順序被正規化，但描述子的變動不會被藏起來
- 格式不對的套件與工具結構會安全地拒絕
- `serverInfo` 維持是診斷用的，永遠不提供准入權威
- 描述子漂移會隔離、停用，並封鎖回滾到那個釘選
- 狀態變動會把有效的釘選隔離
- 回滾選不到一個被隔離或未知的版本
- 帳本被篡改時會被偵測出來

## 生產環境的失敗模式

| 失敗 | 為什麼會發生 | 必要的回應 |
|---|---|---|
| 名稱看起來有效，但命名空間從未被認證 | 政策信了紀錄裡的文字 | 在一個受信任的命名空間驗證器提供出確切前綴之前一律拒絕 |
| 同一個套件座標回傳了新的位元組 | 上游可變，或散布通道被入侵 | 停止啟用、保留兩份摘要、調查那個取回邊界 |
| 「latest」在沒有審查下改變 | 浮動的選擇逃出了釘選 | 只解析那些確切被准入的版本與摘要 |
| 核可之後才出現新工具 | 執行期漂移，或那是另一個部署 | 隔離那條路由，並擷取一次新的描述子觀察 |
| 已棄用的版本仍然有效 | 缺少狀態同步，或同步延遲 | 依排程並在啟用之前調和狀態 |
| 被刪除的紀錄在預設同步裡消失 | 客戶端只要了 active 的紀錄 | 用增量或能察覺 deleted 的調和，並保住本地歷史 |
| 回滾目標從未被准入 | 路由控制跟核可狀態脫節 | 拒絕這次回滾，並為那個目標跑一次新的准入 |
| 攻擊者把所有項目重寫之後帳本在本地照樣驗得過 | 這條雜湊鏈沒有外部錨 | 把已簽署的帳本頭發布到另一個信任域 |
| 證據裡含有 bearer 權杖或工具引數 | 日誌把整個請求抄了進去 | 在收集當下就遮蔽，只存最低限度的證明 |

## 維運準則

發布回答的是「這個身分可以發布這個名稱嗎？」准入回答的是「我們要不要執行這個確切的產物，並暴露這個確切的行為？」把那兩個決策分開、把每一個接合點釘住，並讓回滾去選證據，而不是靠印象。
