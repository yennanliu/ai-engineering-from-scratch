# 自主代理的權限模式

> 一道權限階梯 —— 從「每個行動都審查」到「什麼都核准」的分級自主性 —— 就是執行環境用來治理「自主代理可以不問就做什麼」的方式。本課的實作範例 Claude Code 暴露六種這樣的模式：「plan」在每個行動之前都問，「default」（UI 上標為「Manual」）只在有風險時問，「acceptEdits」自動核准檔案寫入但仍會確認 shell 執行，而「bypassPermissions」什麼都核准。Auto Mode —— 也就是 `auto` 這個權限模式 —— 用一個獨立的分類器模型取代逐行動核准，它會在每個行動執行前先審查，並擋下任何超出請求範圍的升級行為。行動預算則透過 `max_turns` 與 `max_budget_usd` 強制執行。`auto` 是否可用取決於方案、組織是否啟用、模型與供應商 —— 而 Anthropic 明白表示，光靠那個分類器並不足夠。

**類型：** 學習
**程式語言：** Python (stdlib, two-stage classifier simulator)
**先修單元：** 階段 15 · 01（長時程代理）、階段 15 · 09（寫程式代理的版圖）
**時間：** 約 45 分鐘

## 問題所在

一個跑在你機器上的自主寫程式代理，是一個獨立的安全類別。攻擊面是代理搆得到的一切 —— 檔案系統、網路、憑證、剪貼簿、任何瀏覽器分頁、任何開著的終端機。Bruce Schneier 等人已公開標示這件事：computer-use 代理不是聊天機器人的「功能更新」，它們是一種帶有全新風險輪廓的新工具。

Claude Code 的權限系統是 Anthropic 的答案。它不是一個「自主／不自主」的開關，而是六種模式構成的能力階梯：plan → default → acceptEdits → … → bypassPermissions。每一種模式都是速度與逐行動審查之間不同的取捨。Auto Mode（2026 年 3 月）加上一個獨立的分類器模型，把核准移出使用者的關鍵路徑：它在每個行動執行前先審查，並擋下任何超出請求範圍的升級行為。

工程上的問題是：這套系統抓得到什麼、漏掉什麼，以及某項任務實際上該用哪一種模式？

## 核心概念

### 那六種權限模式

| 模式 | 行為 | 何時使用 |
|---|---|---|
| `plan` | 代理提出一份計畫；使用者核准整份計畫；每個行動在執行前都被審查 | 不熟悉的任務；貼近生產的程式碼；第一次在某個儲存庫上用這個代理 |
| `default` | UI 上標為「Manual」。代理執行行動；遇到任何「有風險」的行動（shell 執行、破壞性操作、網路呼叫）就提示使用者 | 多數互動式的寫程式工作階段 |
| `acceptEdits` | 檔案寫入自動核准；shell 執行與網路呼叫仍會提示 | 跨多個檔案的重構 |
| `auto` | 一個獨立的分類器模型在每個行動執行前審查它；擋下任何超出請求範圍的升級行為 | 在受限工作區中長時程、無人看管的執行 |
| `dontAsk` | 從不提示；未被權限規則預先核准的行動一律拒絕 | 短暫沙箱、CI 工作、研究腳本 |
| `bypassPermissions` | 什麼都核准 | 文件寫著「只在你願意丟掉的短暫容器裡使用」 |

（上表名稱與公開的 Claude Code 文件一致；UI 把 `default` 標為「Manual」。）

### 一頁講完 Auto Mode

Auto Mode（2026 年 3 月 24 日推出）是第一個把逐行動核准委派給模型的權限模式。結構：

1. **一個獨立的分類器模型。** 在每個被提議的行動執行前審查它，依據所宣告的任務與工作階段的當前狀態來評判，並擋下任何超出請求範圍的升級行為。被擋下的行動會退回給使用者。
2. **可用性受閘門控制。** `auto` 到底提不提供，取決於方案、組織是否啟用、模型與供應商。

預算控制與分類器並列：

- `max_turns` —— 一個工作階段中的總迭代次數。
- `max_budget_usd` —— 會中止工作階段的金額上限。
- 逐工具的行動次數限制（例如 `WebFetch` 呼叫不得超過 N 次）。

### 這套系統抓得到什麼

- 直白的、注入到工具輸入裡的提示詞注入，且被注入的指令對映到某種已知有風險的行動形狀。
- 重複的工具迴圈 —— 分類器看得出行動 N+1 跟行動 N 幾乎一樣，而且連續五次。
- 在一個本來只做檔案編輯的工作階段中，明顯超出範圍的 shell 指令。

### 這套系統可能漏掉什麼

- **細膩的提示詞注入**，它調變行為卻不產生任何一個被標記的行動。間接提示詞注入不是一個可以完全修補的漏洞（OpenAI 的準備度負責人，2025 年，談瀏覽器代理 —— 見第 11 課）。
- **語意層級的失當行為。** 每一個個別行動都可以看起來安全，而組合起來的軌跡卻是有害的。分類器評判的是行動；它不會把使用者的意圖重新推導一遍。
- **透過合法通道的外洩。** 把資料寫進一個你擁有的檔案，然後 `git push` 到一個公開儲存庫，是一串被允許的行動，問題出在它們的組合。

### 研究預覽的定位

Anthropic 是以研究預覽的形式出貨 Auto Mode。文件明白寫著那個分類器是一層，不是解答：使用者被預期要把 Auto Mode 與預算、允許清單、隔離工作區與軌跡稽核結合起來（第 12–16 課）。研究預覽這個定位也反映了那個被記錄下來的評測與部署落差（第 1 課）—— 一個離線評測過得了的分類器，在使用者脈絡模稜兩可的真實工作階段中，行為可能不同。

### 這道階梯在你的工作流中的位置

- 不熟悉的任務：從 `plan` 開始。讀一份計畫，比回捲一趟壞掉的執行便宜。
- 已知的重構：`acceptEdits` 省下大量確認點擊。
- 無人看管的背景執行：只在你已量測過爆炸半徑的工作區裡用 `auto`（沒有憑證、沒有生產環境掛載、沒有你沒選擇加入的對外流量）。
- 短暫容器：只有在容器與其憑證都是用完即丟時，`dontAsk`／`bypassPermissions` 才可接受。

## 框架應用

`code/main.py` 把一個行動審查分類器模擬成一條兩階段管線 —— 這是教學上的簡化；真正的 `auto` 模式背後是一個獨立的分類器模型，並不是一份有文件的兩階段契約。第 1 階段是對被提議行動做的便宜關鍵字規則；第 2 階段是較慢的多規則審查器。驅動程式餵進一條短短的合成軌跡（安全行動、一次提示詞注入嘗試、一個重複迴圈），並顯示分類器在哪裡抓到、在哪裡漏掉。

## 產出交付

`outputs/skill-permission-mode-picker.md` 把一段任務描述對到正確的權限模式、預算上限與所需的隔離。

## 練習

1. 跑 `code/main.py`。哪一種合成行動型別從來不會被第 1 階段標記、卻總是被第 2 階段抓到？哪一種兩者都抓不到？

2. 擴充第 1 階段的規則集，讓它抓到某個特定的已知有害形狀（例如 `curl $ATTACKER/exfil`）。在良性行動樣本上量偽陽性率。

3. 讀 Anthropic 的〈How the agent loop works〉文件。列出在 `default` 模式下，代理預設會碰到的每一項外部狀態。在無人看管地跑 `auto` 之前，你會需要另外替哪些設閘門？

4. 設計一份 24 小時無人看管執行的預算：`max_turns`、`max_budget_usd`、逐工具上限、允許清單。替每個數字辯護。

5. 描述一條軌跡：其中每一個個別行動都被分類器核准，組合起來的行為卻是失準的。（第 14 課涵蓋斷路開關與金絲雀詞元如何處理這件事。）

## 關鍵術語

| 術語 | 大家怎麼說 | 實際是什麼意思 |
|---|---|---|
| 權限模式 | 「代理能做多少事」 | 六種具名政策之一，控制逐行動的核准 |
| plan 模式 | 「做任何事之前先問」 | 代理寫一份計畫；使用者在執行前核准 |
| acceptEdits | 「讓它寫檔案」 | 檔案寫入自動核准；shell 執行仍會提示 |
| auto | 「自動核准」 | 獨立的分類器模型審查每個行動；擋下超出請求範圍的升級 |
| bypassPermissions | 「全速 YOLO」 | 什麼都核准；為短暫容器而設 |
| 第 1 階段（模擬器） | 「快速關鍵字檢查」 | `code/main.py` 中對被提議行動的便宜規則 |
| 第 2 階段（模擬器） | 「深度審查」 | `code/main.py` 中針對被標記行動的較慢多規則審查器 |
| 研究預覽 | 「不是正式版」 | Anthropic 用來描述「失敗模式仍在盤點中」功能的說法 |
