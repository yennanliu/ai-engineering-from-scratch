# 檢查點與回捲

> 每一次圖狀態轉移都持久化。當某個 worker 崩潰時，它的租約到期，另一個 worker 從最新的檢查點接手。Cloudflare Durable Objects 把狀態撐住數小時到數週。先提議後提交（第 15 課）替每個行動定義一份回捲計畫。事後查證把迴圈收攏。歐盟 AI 法案第 14 條讓高風險系統的有效人類監督成為強制 —— 實務上這意味著檢查點必須可查詢、回捲必須演練過，而稽核軌跡必須撐得過一次部署。那個尖銳的失敗模式是：沒有冪等鍵與前置條件檢查，一次暫時性失敗之後的重試，就可能把一項已核准的行動執行兩次。事後查證正是抓到它的東西。

**類型：** 學習
**程式語言：** Python (stdlib, checkpoint and rollback state machine)
**先修單元：** 階段 15 · 12（持久執行）、階段 15 · 15（先提議後提交）
**時間：** 約 60 分鐘

## 問題所在

持久執行（第 12 課）讓崩潰的代理可以續跑。先提議後提交（第 15 課）讓已核准的行動可以稽核。這一課把兩者接起來：當一項已核准的行動執行到一半、崩潰、然後續跑時，會發生什麼事？回捲什麼時候跑，又是針對哪個狀態跑？

真實系統的接法各不相同：

- **LangGraph** 把每一次圖狀態轉移存成檢查點到 PostgreSQL。worker 崩潰時，租約釋出，另一個 worker 從最新檢查點續跑。工作流在 `interrupt()` 時暫停，而那件事本身也會被持久化。
- **Cloudflare Durable Objects** 以鍵為單位把狀態撐住數小時到數週。把運算與那項已核准行動的儲存放在一起。
- **Microsoft Agent Framework** 在工作流 API 中暴露 `Checkpoint` 原語；重播加冪等性涵蓋重試。

在每個案例中，真正管用的組合都是：冪等鍵（防止重複執行）+ 前置條件檢查（狀態仍然是我們當初核准時的樣子）+ 事後查證（副作用真的發生了）+ 查證失敗時回捲。

## 核心概念

### 每一次轉移都持久化

圖狀態轉移是指任何把工作流從一個具名狀態帶到另一個具名狀態的步驟。天真的實作只在特定提交點持久化；生產實作則持久化每一次轉移。那個成本（多幾次寫入）相對於可靠度收穫（重播可以落在任何地方、租約復原很精確）是很小的。

### 租約復原

當某個 worker 崩潰時，工作流並沒有遺失；只是那份租約（一份「這個 worker 正在執行這趟」的短命宣告）到期了。另一個 worker 接手最新檢查點並續跑。租約機制正是讓生產系統能撐過滾動部署而不遺失進行中工作的東西。

### 冪等性加前置條件

光有冪等性不夠。想想看：一個工作流被核准為「當餘額 > 1000 美元時，從 A 轉 100 美元給 B」。這個工作流被提交、在執行中途崩潰，然後續跑。若只檢查冪等鍵，執行續跑，轉帳就跑一次（正確）。但假設在崩潰與續跑之間，A 的餘額因為另一條工作流掉到了 500 美元。冪等檢查依然通過；前置條件則不通過。沒有前置條件檢查，我們就出貨了一次透支。

每一項有後果的行動都需要兩者：

- **冪等鍵**：防止重複執行。
- **前置條件檢查**：確認狀態仍與當初核准的一致。

### 事後查證

「工具回傳 200」不是查證。真正的查證會重新讀取目標狀態，並確認那個副作用真的發生了。模式：

- 資料庫更新：`UPDATE ... RETURNING *`，然後斷言回傳的那一列符合預期狀態。
- 寄信：送出後到寄件備份中檢查該訊息 ID。
- 寫檔案：把檔案讀回來並算雜湊。
- API 呼叫：對目標資源做一次後續 `GET`。

若查證失敗，工作流就處在一個已知的壞狀態。回捲啟動。

### 回捲計畫

先提議後提交（第 15 課）中每一項有後果的行動，都帶一份回捲計畫。型別：

- **帶內回捲**：直接把副作用反轉（`INSERT` 後 `DELETE`、寄出後再寄一封更正信）。
- **補償交易**：一項用來中和原行動的新行動（標準的 SAGA 模式）。
- **帶外回捲**：警示一個人、暫停工作流，把壞狀態留著供調查。

無法回捲（「我們沒辦法把它復原」）必須在提議中被點名。沒有回捲的行動，在提交時需要更強的 HITL（第 15 課的挑戰—回應）。

### 歐盟 AI 法案第 14 條的運維解讀

第 14 條要求高風險系統要有「有效的人類監督」。在運維語言中，實作者是這樣讀它的：

- 檢查點可以被稽核者查詢。
- 回捲有被演練過（至少端到端測過一次）。
- 稽核軌跡撐得過一次部署（檢查點後端不是短暫的）。
- 查證失敗會發警示，不是靜靜寫進日誌。

一條在提交中途崩潰、續跑、然後在沒有查證 + 回捲路徑的情況下完成副作用的工作流，過不了第 14 條這關。

### 那個尖銳的失敗模式：重複執行

這個領域最常見的生產事故：

1. 行動被核准，冪等鍵為 k。
2. 提交開始、執行、回傳 200。
3. 工作流在持久化「已提交」狀態之前崩潰。
4. 工作流續跑；看到「已核准但未提交」；重新執行。
5. 副作用觸發兩次。

緩解方式：在執行之前先持久化一個「進行中」的意圖、帶著冪等鍵執行，然後只有在事後查證成功之後才標記為「已提交」。若行動觸發了但狀態寫入失敗，你知道要去查證、必要時重新觸發。若狀態寫入成功而行動失敗，你就透過復原路徑去查證並恰好觸發一次。

## 框架應用

`code/main.py` 實作一條帶檢查點的工作流，含冪等性、前置條件、查證與回捲。驅動程式模擬四種情境：乾淨執行、崩潰後重試（被冪等性接住）、前置條件失敗（工作流在不觸發的情況下中止）、查證失敗（回捲觸發）。

## 產出交付

`outputs/skill-rollback-rehearsal.md` 替一條被提議的工作流設計一次回捲演練測試，並稽核檢查點後端的稽核軌跡持久性。

## 練習

1. 跑 `code/main.py`。驗證那四種情境。對於「提交中途崩潰」那一種，確認跨多次重試該行動恰好觸發一次。

2. 把「先標記完成、再去做」這個模式改成狀態寫入在行動之後才觸發。重跑崩潰情境。量有幾次重複行動被觸發。

3. 替一項特定的生產行動（例如「發文到某個 Slack 頻道」）設計一份回捲計畫。把它分類為帶內、補償或帶外。替你的選擇辯護。

4. 挑一條你熟悉的工作流。指認出它的每一次狀態轉移。替每一次標上持久性需求（持久化／不持久化）。數一數你目前沒有持久化的那些。

5. 演練過的回捲測試：設計一項端到端測試，跑一條真實工作流、讓它崩潰，並確認回捲路徑有觸發。這項測試斷言什麼？

| 租約 | 「Worker 的宣告」 | 「某個 worker 正在執行某趟」的短命宣告；崩潰時到期 |

| 事後查證 | 「重讀檢查」 | 確認副作用真的在目標系統裡發生了 |

| 補償交易 | 「SAGA 式復原」 | 一項用來中和原行動的新行動 |
