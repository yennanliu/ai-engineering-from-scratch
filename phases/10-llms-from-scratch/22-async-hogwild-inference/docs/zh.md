# 非同步與 Hogwild! 推論

> 推測式解碼（階段 10 · 15）是在一條序列**內部**平行處理詞元。多代理程式框架則跨整條序列做平行，但必須明確協調（投票、切分子任務）。Hogwild! 推論（Rodionov 等人，arXiv:2504.06261）走的是另一條路：讓同一個 LLM 的 N 個實例平行跑，共用同一份 key-value 快取。每個工作者都能立刻看到其他所有工作者生成的詞元。現代的推理模型 —— QwQ、DeepSeek-R1 —— 完全不用微調，就能透過這份共享快取自行協調。這個做法還處於實驗階段，但它開出一條全新的推論平行化軸線，和推測式解碼互不衝突。本單元用 stdlib Python 實作一個雙工作者的 Hogwild! 模擬器，並解釋為什麼這種共享快取式的協作，是從模型既有的推理能力中自然浮現出來的。

**類型：** 實作
**程式語言：** Python (stdlib)
**先修單元：** 階段 10 · 12（推論最佳化）、階段 10 · 15（推測式解碼）
**時間：** 約 60 分鐘

## 學習目標

- 描述三種常見的平行 LLM 拓撲（投票、子任務、Hogwild!），並說出每一種各自針對什麼問題。
- 說明 Hogwild! 的核心設定：多個工作者、一份共享 KV 快取、透過自我提示浮現的協調行為。
- 把 Hogwild! 的實際耗時加速比，寫成工作者數量 `N`、任務層級平行度 `p` 與協調開銷 `c` 的函式。
- 在一個玩具問題上實作雙工作者的 Hogwild! 模擬器，觀察自然浮現的任務分工。

## 問題所在

現代 LLM 解難題的方式，是產出很長的推理鏈 —— 5000 個詞元的逐步邏輯很常見，深度數學問題則會出現數萬個詞元。在 70B 模型上以每秒 35 個詞元解碼，5 萬個詞元要跑 24 分鐘。這種模型談不上互動。

推測式解碼（階段 10 · 15）靠著在一條序列內部做平行，帶來 3 到 5 倍的加速。再往上，自迴歸解碼的序列相依性就是一道硬天花板。每個新詞元都取決於它前面的每一個詞元。

那顯而易見的問題就是：我們能不能跨序列做平行？在同一個問題上跑同一個模型的多個副本，讓它們互相合作、把工作分掉？

先前的做法有：投票式集成（跑 N 個模型，取多數答案）、思維樹（分岔出多條推理路徑再重組），以及多代理程式框架（指派每個代理程式一項子任務，另有一個協調者）。這些在特定任務領域都有幫助，但也都引進了明確的協調機制 —— 投票規則、分岔與剪枝邏輯、代理程式之間的訊息協定。

Hogwild! 推論的路數不同。N 個工作者共用單一份 KV 快取。每個工作者都能立即看到其他工作者生成的詞元，就像那是它自己的脈絡一樣。這些工作者 —— 完全沒有經過訓練或微調 —— 會自己想出怎麼分工。現代推理模型（QwQ、DeepSeek-R1、Claude 家族的推理模式）能讀取共享快取，然後講出「我看到工作者 2 已經處理掉基礎情形了，那我來做歸納步驟」這種話。

加速幅度取決於工作負載，而且到 2026 年 4 月為止仍屬實驗性質。但這個想法值得認識，因為它開出了一條新的推論平行化軸線。

## 核心概念

### 基本設定

初始化 N 個工作者行程，全都跑同一個 LLM。不再讓每個工作者各持一份 KV 快取，而是維護**一份**共享快取。當工作者 `i` 生成詞元 `t_j` 時，這個詞元會被寫進共享快取的下一個位置。當工作者 `k` 邁出下一步時，它讀到的是快取當下的狀態（其中包含全部 N 個工作者到目前為止生成的一切）。

在每一步中，工作者會競相寫入詞元。這裡沒有逐工作者的位置索引 —— 快取就是一條不斷長大的序列，順序由寫入抵達的時間決定。

### 協調為什麼會自然浮現

工作者共用同一段提示詞，通常長得像「你是共同處理這個問題的 N 個實例之一。每個實例都會讀取共享記憶體，也能看見其他實例寫了什麼。請避免重複的工作。」提示詞加上共享快取就夠了。推理模型會讀取快取、注意到問題的哪些部分已經有人嘗試過，然後（通常會，但不是每次都會）轉向還沒被探索的部分。

Hogwild! 論文（Rodionov 等人，2025）記錄到這類觀察：

- 工作者會制定計畫，並透過快取傳達給其他工作者。
- 工作者會注意到其他工作者推理中的錯誤，並指出來。
- 計畫失敗時，工作者會調整並提出替代方案。
- 被提示要檢查是否重複時，工作者能偵測到重複並轉向。

這些都不需要微調。這些浮現行為來自模型本來就具備的推理能力。

### 名字的由來

這篇論文的名字致敬 Hogwild! SGD（Recht 等人，2011），一種非同步更新的最佳化器。類比是這樣的：SGD 的非同步工作者全都寫入一個共享的參數向量；Hogwild! 推論的工作者則全都寫入一份共享的 KV 快取。兩者靠的都是實測上的收斂，而不是同步化保證。

### RoPE 讓這件事變得可行

旋轉位置嵌入（RoPE，Su 等人 2021）透過對 Q 與 K 向量做旋轉來編碼位置資訊。因為位置是旋轉而不是寫死的偏移量，所以一個詞元的位置可以移動，而不必重算 KV 快取條目。當工作者 `i` 在位置 `p` 寫進共享快取時，其他讀到那個位置的工作者可以直接使用快取條目 —— 不需要重新旋轉。

換成學習式位置或絕對位置的模型，Hogwild! 就得在每一次並行寫入時做快取失效處理。RoPE 讓快取能保持穩定。

### 實際耗時的計算

令 `T_serial` 為單一工作者獨力解完問題所需的時間，`p` 為任務層級可平行化的比例，`c` 為每一步的協調開銷（讀取變長的快取、決定要寫什麼）。

單工作者時間：`T_serial`。
N 個工作者的 Hogwild! 時間，假設協調免費：`T_serial * ((1 - p) + p / N)`。這就是經典的 Amdahl 定律。
加上協調開銷：`T_serial * ((1 - p) + p / N) + c * steps_per_worker`。

工作者要能真的有產出，`c` 相對於每步解碼時間就必須夠小。在會產出 5k 以上詞元的推理模型上，工作者花上幾百個詞元的協調開銷仍然划算。在短對話任務上，協調開銷會主導一切，Hogwild! 反而比序列執行還糟。

### 具體例子

推理問題：1 萬個詞元的思維鏈。假設問題中可平行化的內容為 `p = 0.7`（不同的證明策略、不同的分類討論），每個工作者的協調開銷為 `c = 200` 個詞元。取 `N = 4` 個工作者：

- 序列時間：10000 個解碼步驟。
- Hogwild! 時間：10000 * (0.3 + 0.7 / 4) + 200 * 4 = 10000 * 0.475 + 800 = 5550 個解碼步驟。
- 加速比：10000 / 5550 = 1.8 倍。

這算是不高。但在更長的推理問題上（5 萬個詞元），協調開銷被攤提掉，加速比會逼近 2.5 到 3 倍。Hogwild! 之於推論，就相當於在一種能自然寫多執行緒程式碼的語言中的執行緒層級平行。

### 什麼時候該用 Hogwild!

- 長推理問題（數千個詞元），而且任務可以拆成多個獨立子目標來平行處理。
- 已經被訓練成逐步思考的推理模型。非推理模型沒辦法好好自我協調。
- 單節點部署，且 VRAM 足以容納共享快取加上 N 個工作者行程。快取是共享的，但每個工作者有自己的激活值記憶體。

### 什麼時候不該用

- 短互動對話。協調開銷會主導一切。
- 無法平行化的任務（單一條線性證明、單一次編譯）。N=1 就是上限。
- 非推理模型。不會浮現任何協調行為。
- 多節點部署。共享快取需要極快的跨工作者同步。同節點內沒問題；跨節點則是延遲上的災難。

### 實驗性的現況

截至 2026 年 4 月，Hogwild! 是一套帶有開源 PyTorch 實作的研究方法，尚未進入生產環境。有三個阻礙：

1. 在多個並行行程之間管理共享 KV 快取，在工程上並不簡單。
2. 浮現式協調與任務高度相關；相關基準測試還在建立中。
3. 相較於推測式解碼已經帶來的效果，這個加速幅度並不大；兩者可以合併，但合併後的工程又多了一層。

值得認識，值得實驗，但還不值得押上一整個產品。

## 動手實作

`code/main.py` 實作了一個玩具版的 Hogwild! 模擬器：

- 兩個工作者行程，各自是一個決定性的「LLM」，會以已知的機率產出數種詞元類別之一（工作詞元、觀察詞元、協調詞元）。
- 一份共享快取（就是一個詞元串列），兩個工作者都會讀寫。
- 一套簡單的協調邏輯：當某個工作者看到另一個工作者已經在某個類別產出足夠多的工作詞元時，它就換一個類別。

模擬器會跑固定的步數預算，並回報：

- 產出的工作詞元總數。
- 總耗時（工作者步數）。
- 相對於單一工作者的有效加速比。
- 一份追蹤紀錄，記下每個詞元是哪個工作者寫的。

### 步驟 1：共享快取

一個兩個工作者都會附加寫入的串列。真實實作中會用簡單的鎖（Python 的 `threading.Lock`）；我們這裡用一個計數器來模擬。

### 步驟 2：工作者迴圈

每個工作者在每一步中：

- 讀取當前的共享快取。
- 根據裡面已有的內容，決定要寫哪一類的詞元。
- 寫入一個詞元。

### 步驟 3：協調啟發式規則

如果類別 X 在快取中已經有 K 個詞元，而工作者原本打算寫的類別就是 X，那它就改寫類別 Y。這是推理模型那種「注意到這塊已經有人做了，換做別的」行為的玩具版替身。

### 步驟 4：量測加速比

在相同的總步數預算下，分別用 N=1 與 N=2 個工作者跑模擬器，數出產出的工作詞元數量。由於協調帶動的任務分工，N=2 應該會多產出約 1.5 到 1.8 倍的工作詞元。

### 步驟 5：對協調機制施壓

調低協調啟發式規則的敏感度，再跑一次。你會看到，少了良好的協調，N=2 會重複產出同樣的詞元，加速比掉到 1 以下。這與論文的觀察吻合：這招只有在工作者具備足以自我協調的推理能力時才成立。

## 框架應用

截至 2026 年 4 月，Hogwild! 在生產環境的整合仍屬研究等級。Yandex／HSE／IST 的參考實作以 PyTorch 為基礎，針對的是 DeepSeek-R1 與 QwQ 模型上的單節點多行程設定。

務實的採用路徑：

1. 剖析你的推理任務工作負載。量測其中屬於探索性（多種策略、分類討論、搜尋）的詞元比例，相對於線性推進的比例有多少。
2. 如果探索佔主導，就跑一次雙工作者的 Hogwild! 實驗，量測實際耗時的改善。
3. 如果改善不到 1.3 倍，代表你落在協調開銷主導的區間。退回單工作者。
4. 如果改善超過 1.5 倍，就推到 N=4 再量一次。報酬遞減通常出現在 N=4 到 8 附近。

與推測式解碼合併使用：每個 Hogwild! 工作者都能各自使用推測式解碼。兩種加速（大致上）會相乘，把 3 倍的推測式解碼與 1.8 倍的 Hogwild! 湊成相對於天真單工作者解碼的 5.4 倍有效加速。

## 練習

1. 以預設設定執行 `code/main.py`。確認在相同耗時下，N=2 的 Hogwild! 設定產出的工作詞元比 N=1 基準更多。

2. 調低協調啟發式規則的強度（設定 `coordination_weight=0.1`），重跑一次，展示加速比如何崩掉。解釋原因：無法協調時，工作者會做重複的功。

3. 計算一個 5 萬詞元推理任務在 `p=0.8, c=500`、N=4 個工作者下的預期 Hogwild! 加速比。再對一個 1 千詞元的對話任務在 `p=0.3, c=200`、N=4 下算一次。為什麼一個划算、另一個賠本？

4. 讀 Hogwild! 論文的第 4 節（初步評估）。找出作者回報的兩種失效模式，並描述一個更好的協調提示詞可以怎麼各自緩解它們。

5. 在這個玩具實作中把 Hogwild! 與推測式解碼合起來：每個工作者內部使用 2 個詞元的推測式解碼。回報相乘後的加速比。當兩個工作者都想延伸同一段共享快取前綴時，會冒出什麼樣的記帳問題？

## 關鍵術語

| 術語 | 大家怎麼說 | 實際上是什麼 |
|------|----------------|------------------------|
| Hogwild! | 「平行工作者、共享快取」 | 同一個 LLM 的 N 個實例並行執行，共用一份 KV 快取；透過自我提示浮現出協調行為 |
| 共享 KV 快取 | 「協調的媒介」 | 一份不斷長大、由所有工作者共同讀寫的 KV 緩衝區；讓詞元能在工作者之間即時可見 |
| 浮現式協調 | 「不用訓練」 | 具備推理能力的 LLM 能讀取共享快取並自行分工，不需要任何微調或明確的協定 |
| 協調開銷（c） | 「花在搞清楚狀況的詞元」 | 每個工作者讀取變長的快取、決定接下來做什麼的成本；相對於總解碼時間必須夠小 |
| 可平行化比例（p） | 「哪些可以平行跑」 | 任務層級的平行度：整體工作中不具本質序列性的那一部分比例 |
| RoPE 讓 Hogwild! 成立 | 「旋轉位置具備平移不變性」 | 因為位置是旋轉，寫入共享快取時不必重算先前的詞元 |
| 投票式集成 | 「跑 N 個，取多數」 | 最簡單的平行推論拓撲；對分類有用，對長篇推理則用處不大 |
| 思維樹 | 「分岔與剪枝」 | 探索多條分支再剪枝的推理策略；帶有明確的協調邏輯 |
| 多代理程式框架 | 「指派子任務」 | 每個代理程式拿到一個角色，由協調者統籌；協定開銷很重 |
