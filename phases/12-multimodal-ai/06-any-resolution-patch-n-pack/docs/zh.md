# 任意解析度視覺：Patch-n'-Pack 與 NaFlex

> 真實世界的影像不是 224x224 的方塊。收據是 9:16，圖表是 16:9，醫療掃描可能是 4096x4096，手機截圖是 9:19.5。2024 年之前 VLM 的答案 —— 把所有東西縮放成固定的正方形 —— 丟掉的正是讓 OCR、文件理解與高解析度場景解析能運作的那些訊號。NaViT（Google，2023）證明了你可以用區塊對角遮罩，把不同解析度的 patch 打包進單一個 Transformer 批次。Qwen2-VL 的 M-RoPE（2024）則徹底捨棄了絕對位置表。LLaVA-NeXT 的 AnyRes 把高解析度影像鋪排成「基礎圖 + 子影像」。SigLIP 2 的 NaFlex 變體（2025）如今是那些想用單一檢查點服務所有長寬比的開放 VLM 的預設編碼器。這一課會把 patch-n'-pack 從頭到尾實作一遍。

**類型：** 實作
**程式語言：** Python (stdlib, patch packer + block-diagonal mask)
**先修單元：** 階段 12 · 01（ViT patch）、階段 12 · 05（LLaVA）
**時間：** 約 120 分鐘

## 學習目標

- 把一批不同解析度影像的 patch 打包成單一序列，並建出區塊對角注意力遮罩。
- 針對給定任務，在 AnyRes 鋪排（LLaVA-NeXT）、NaFlex（SigLIP 2）與 M-RoPE（Qwen2-VL）之間做選擇。
- 在不縮放尺寸的前提下，為 OCR、圖表與攝影照片算出詞元預算。
- 說出方形縮放的三種失敗模式：文字被壓扁、內容被裁掉、詞元浪費在填補上。

## 問題所在

Transformer 期待的是序列。一個批次就是一疊等長的序列。如果你的影像都是 224x224，你每次都拿到 196 個 patch 詞元，不必填補，收工。在 224 上訓練，在 224 上推論，從此不必再想解析度的事。

但這個世界不配合。文件是直式的（8.5x11 英吋，大約 2:3）。圖表截圖是橫式的（16:9）。收據又高又瘦（1:3）。醫療影像出廠就是 2048x2048 或更大。行動裝置截圖是 1170x2532（0.46:1）。

2024 年之前的三種選項，以及它們各自為何失敗：

1. 縮放成固定正方形（224x224 或 336x336）。壓扁會扭曲文字與臉孔。降採樣會摧毀圖表標籤與 OCR 內容。這是 LLaVA-1.5 之前的標準做法。
2. 裁切成固定長寬比。你會丟掉影像的大部分，而且該裁哪裡本身又是一個視覺問題。
3. 填補到最長邊。這解決了扭曲，但直式影像會有超過 50% 的詞元浪費在填補上。而且那些填補詞元還要付平方複雜度的注意力代價。

2024 到 2025 年的答案是：讓 Transformer 以影像的原生解析度吃下 patch，再想辦法把一個異質批次打包成單一序列而不浪費計算。

## 核心概念

### NaViT 與 patch-n'-pack

NaViT（Dehghani 等人，2023）是證明這招在規模上行得通的那篇論文。想法很機械化：

1. 對批次中的每張影像，在選定的 patch 大小（比方說 14）下算出它的原生 patch 網格。
2. 把每張影像的 patch 攤平成它自己那條長度不一的序列。
3. 把所有影像的 patch 串接成這一批的一條長序列。
4. 建一個區塊對角注意力遮罩，讓影像 A 的 patch 只在影像 A 內部互相關注。
5. 帶上每個 patch 的位置資訊（2D RoPE 或分數式位置嵌入）。

一批三張影像，分別是 336x336（576 詞元）、224x224（256 詞元）與 448x336（768 詞元），會變成一條 1600 詞元的序列，配上一個 1600x1600 的區塊對角遮罩。不必填補。不浪費計算。Transformer 應付得了任意長寬比。

NaViT 還引入了訓練期間的分數式 patch 丟棄 —— 在整批中隨機丟掉 50% 的 patch —— 這既能正則化又能加速訓練。SigLIP 2 繼承了這一招。

### AnyRes（LLaVA-NeXT）

LLaVA-NeXT 的 AnyRes 是務實的替代方案。給定一張高解析度影像與一個固定的編碼器（336 解析度的 CLIP 或 SigLIP），把影像鋪排開來：

1. 從一組預先定義的格局中 —— (1x1)、(1x2)、(2x1)、(1x3)、(3x1)、(2x2) 等等 —— 挑一個最貼合這張影像長寬比的網格。
2. 把整張影像鋪排到該網格上；每一格變成一塊 336x336 的裁切。
3. 另外產出一張縮圖：把整張影像縮放到 336x336，當作全域脈絡的詞元。
4. 把每一格都送進凍結的 336 編碼器。把各格詞元 + 縮圖詞元串接起來。

以一張 672x672 的影像用 2x2 網格加縮圖為例：4 * 576 + 576 = 2880 個視覺詞元。昂貴但有效 —— LLM 同時看到局部細節與全域脈絡。

當你的編碼器是凍結的、而且只支援單一解析度時，AnyRes 就是首選路線。它會讓大影像的詞元數爆炸（一張 1344x1344 的影像用 4x4 網格就是 9216 + 576 ≈ 9800 個詞元，這幾乎填滿一個 8k 的 LLM 脈絡）。

### M-RoPE（Qwen2-VL）

Qwen2-VL 引入了多模態旋轉位置嵌入。不同於 NaViT 的分數位置或 AnyRes 的鋪排加縮圖，這裡每個 patch 都帶一個三維位置（時間、高、寬）。query／key 的旋轉能應付任意的 H、W 與時間長度。

M-RoPE 不必重訓就原生支援動態解析度。推論時你餵進任何 HxW 的影像，patch 嵌入器產出 H/14 x W/14 個詞元，每個詞元拿到自己的 (t=0, r=列, c=行) 位置，RoPE 用對應的頻率去旋轉注意力，完成。Qwen2.5-VL 與 Qwen3-VL 延續了這個做法。InternVL3 的 V2PE 是同樣的想法，只是每個模態的編碼方式可變。

與 AnyRes 不同，M-RoPE 在原生解析度下是 O(H x W / P^2) 個詞元 —— 沒有鋪排帶來的乘法級開銷。而與 NaViT 不同的是，它每次前向仍然只吃一張影像。要跨解析度做批次處理，上面還是得再疊一層 patch-n'-pack。

### NaFlex（SigLIP 2）

NaFlex 是 SigLIP 2 檢查點的原生彈性模式。單一模型在推論時可服務多種序列長度（256、729、1024 個詞元）。它內部在訓練時用的是 NaViT 式的 patch-n'-pack，並為每個 patch 用絕對的分數位置。賣點是：一個檢查點，推論時依任務挑你的詞元預算。

語意類任務（分類、檢索）用 256 個詞元。OCR 或圖表理解用 1024 個詞元。不必重訓。

### 打包遮罩

區塊對角遮罩是多數實作絆倒的地方。對一條總長 `N_total`、涵蓋影像 `i=0..B-1`（各長 `n_i`）的打包序列來說，形狀為 `(N_total, N_total)` 的遮罩 `M`，在兩個索引落在同一張影像的區塊內時為 1，否則為 0。你可以從一份累積長度清單把它建出來：

```
offsets = [0, n_0, n_0+n_1, ..., N_total]
M[i, j] = 1 iff there exists b where offsets[b] <= i < offsets[b+1] and offsets[b] <= j < offsets[b+1]
```

在 PyTorch 裡用 `torch.block_diag` 或明確的 gather，這是一行程式。FlashAttention 的變長路徑（`cu_seqlens`）則完全跳過遮罩，直接用累積長度張量在各序列內部做注意力 —— 以典型批次而言，比稠密遮罩快約 10 倍。

### 詞元預算

依任務挑你的策略：

- OCR／文件：1024 到 4096 個詞元。SigLIP 2 NaFlex 開 1024，或用 AnyRes 3x3 + 縮圖。
- 圖表與 UI：在 384 到 448 的原生解析度下用 729 到 1024 個詞元。Qwen2.5-VL 的動態解析度搭配 max pixels 上限。
- 自然照片：256 到 576 個詞元就夠了。下游的 LLM 看到的資訊已經足夠。把詞元花在內容密度高的地方。
- 影片：空間池化後每畫格 64 到 128 個詞元，2 到 8 FPS。單元 12.17 會談這個。

2026 年的生產守則：為每種任務挑一個 max-pixels 上限，在該上限之內以原生長寬比編碼，把批次打包起來，並跳過填補。Qwen2.5-VL 開放 `min_pixels` 與 `max_pixels`，就是給你調這個旋鈕的。

## 框架應用

`code/main.py` 為一批帶整數像素座標的異質影像實作了 patch-n'-pack。它會：

- 接收一串 (H, W) 影像尺寸。
- 在 patch 大小 14 之下，算出每張影像的 patch 序列長度。
- 把它們打包成一條總長 `sum(n_i)` 的序列。
- 建出區塊對角注意力遮罩（用稠密形式，方便看清楚）。
- 把打包後的成本，與方形縮放和 AnyRes 鋪排做比較。
- 為一個混合批次（收據、圖表、截圖、照片）印出一張詞元預算表。

跑跑看。掉出來的那些數字，就是 2026 年每個開放 VLM 都用 patch-n'-pack 的原因。

## 產出交付

這一課產出 `outputs/skill-resolution-budget-planner.md`。給定一份長寬比混雜的工作負載（OCR、圖表、照片、影片畫格）與一個總詞元預算，它會挑出對的策略（NaFlex、AnyRes、M-RoPE 或固定方形），並產出逐請求的設定。當你在為一個產品估算 VLM 規格時就用這項技能 —— 它能避免那種悄悄發生、把延遲預算殺光的 10 倍詞元暴增。

## 練習

1. 一張收據是 600x1500（1:2.5）。在 patch 大小 14 之下，原生解析度有多少詞元？方形縮放到 336 之後又有多少？實務上哪一種在 OCR 準確率上損失更多？

2. 為一批長度分別是 256、576、729、1024 的四張影像建出區塊對角遮罩。驗證注意力矩陣是 2585x2585，且恰好有 `256^2 + 576^2 + 729^2 + 1024^2` 個非零元素。

3. 對一張 patch 14 的 1792x896 影像，比較：(a) 方形縮放到 336 再編碼、(b) AnyRes 2x1 + 縮圖、(c) 原生解析度的 M-RoPE。哪一個用的詞元最少？哪一個保留最多細節？

4. 實作分數式 patch 丟棄：給定一條打包序列，均勻隨機丟掉 50% 的詞元，並相應更新區塊對角遮罩。量測遮罩稀疏度的變化。

5. 讀 Qwen2-VL 論文（arXiv:2409.12191）第 3.2 節。用兩句話描述 `min_pixels` 與 `max_pixels` 各自控制什麼，以及為什麼上下界兩者都重要。

## 關鍵術語

| 術語 | 大家怎麼說 | 實際上是什麼 |
|------|-----------------|------------------------|
| Patch-n'-pack | 「NaViT 式打包」 | 把不同影像那些長度不一的 patch 序列，串接進同一個批次維度 |
| 區塊對角遮罩 | 「打包遮罩」 | 一種注意力遮罩，把每張影像的 patch 限制成只關注自己，而非打包中的鄰居 |
| AnyRes | 「LLaVA-NeXT 鋪排」 | 把高解析度影像切成固定大小的鋪排網格再加一張全域縮圖；每一格都用固定編碼器編碼 |
| NaFlex | 「SigLIP 2 原生彈性」 | 單一 SigLIP 2 檢查點，推論時不必重訓就能服務 256／729／1024 的詞元預算 |
| M-RoPE | 「多模態 RoPE」 | 三維旋轉位置編碼（時間、列、行），不用位置表就能應付任意的 H、W、T |
| cu_seqlens | 「FlashAttention 打包」 | FlashAttention 變長路徑用來取代稠密區塊對角遮罩的累積長度張量 |
| min_pixels／max_pixels | 「解析度上下界」 | Qwen2.5-VL 的逐請求旋鈕，為極小或極大的輸入設定詞元數上限 |
| 視覺詞元預算 | 「每張影像幾個詞元」 | 每張影像吐出的 patch 詞元數的粗估；它決定了 LLM 的提示詞預算與注意力成本 |
