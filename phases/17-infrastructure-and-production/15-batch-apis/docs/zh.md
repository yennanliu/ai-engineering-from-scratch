# 批次 API —— 那個成為業界標準的 50% 折扣

> 每家主要供應商都出貨了一套非同步批次 API，打五折、約 24 小時周轉。OpenAI、Anthropic、Google，以及多數推論平台（Fireworks 的批次層級、Together 的批次）實作的都是同一套模式。把批次與提示詞快取疊起來，隔夜管線就降到同步未快取成本的約 10%。規則殘酷地簡單：只要不是互動式的，它就屬於批次。內容生成管線、文件分類、資料抽取、報告生成、大量標註、目錄標籤 —— 任何忍得住 24 小時延遲的東西，在搬到批次之前都是把錢留在桌上。2026 年的生產模式是把每一項新的 LLM 工作負載檢傷分類到三條車道：互動式（同步配快取）、半互動式（非同步佇列配退路）、批次（隔夜、疊上快取輸入）。那些假裝自己是互動式、實際上忍得住好幾分鐘延遲的工作負載，浪費得最多。

**類型：** 學習
**程式語言：** Python (stdlib, toy batch-vs-sync cost simulator)
**先修單元：** 階段 17 · 14（提示詞與語意快取）
**時間：** 約 45 分鐘

## 學習目標

- 說出那三套供應商批次 API（OpenAI、Anthropic、Google），以及共通的 50% 折扣加 24 小時周轉保證。
- 算出在一份隔夜分類工作負載上把批次與快取輸入疊起來的成本，並與同步未快取的基線比較。
- 把一項工作負載檢傷分類成互動式／半互動式／批次，並論證那條車道。
- 說出那兩個陷阱：部分互動性（使用者期待比 24 小時更快）與輸出 schema 漂移（各供應商的批次檔案格式不同）。

## 問題所在

你的團隊出貨了一條夜間報告生成管線。5 萬份文件、逐份摘要、把摘要分群、草擬一份主管簡報。同步跑要 4 小時，每晚 2,000 美元。你聽說了批次 API。

批次給你打五折。你同時替系統提示詞（跨全部 5 萬次呼叫共用）啟用提示詞快取。疊起來，帳單掉到每晚 180 美元 —— 約基線的 9%。同一條管線，三項設定改動。

批次是 LLM 成本工具箱裡最便宜、卻沒人去拉的那根槓桿。原因多半是組織性的：團隊心裡想的是「即時」，而 SLA 其實是「早上以前給我」。這一課講的就是「不要把帳單的 90% 留在桌上」。

## 核心概念

### 那三套批次 API

**OpenAI Batch API**：上傳一份含請求清單的 JSONL 檔。承諾 24 小時周轉（實務上通常約 2-8 小時）。輸入與輸出詞元都打五折。`/v1/batches` 端點。符合快取條件的輸入還能再疊上快取輸入定價。

**Anthropic Message Batches**：上傳 JSONL。24 小時周轉。打五折。支援 `cache_control` —— 快取寫入是明確的，讀取在批次內自動發生。

**Google Vertex AI Batch Prediction**：以 BigQuery 或 GCS 為輸入。Gemini 同樣打五折。與 Vertex 的管線整合。

### 語意上：非同步，不是慢

批次是「我承諾在 24 小時內回給你」—— 不是「這件事要花 24 小時」。典型 P50 是 2-6 小時。供應商會把你的批次排在 GPU 存量閒置的離峰窗口。

### 與快取疊起來

一份用同一段 4K 詞元系統提示詞、對 5 萬份文件做摘要的工作：

- 同步未快取：5 萬 × ($輸入 × 4000 + $輸出 × 200)，全額費率。
- 同步已快取：系統提示詞在第一次寫入後被快取；其餘 49999 次輸入便宜 10 倍。
- 批次已快取：以上全部，再加上讀寫都打五折。

疊起來：批次 + 快取 = 同步未快取帳單的約 10%。任何隔夜跑、又有共用系統提示詞的工作負載，都該用這一套。

### 工作負載的檢傷分類

**互動式** —— 使用者在等回應。TTFT 要緊。同步呼叫配提示詞快取。不能批次。

**半互動式** —— 使用者送出一項任務，過幾分鐘回來看。非同步佇列，批次不可用時退回同步。想想中等量的 RAG 建索引。

**批次** —— 使用者期待「早上」或「下一小時」拿到結果。內容管線、規模化分類、離線分析。永遠批次、永遠疊上快取。

常見錯誤：因為那是生產管線，就把所有東西都歸類成互動式。生產不是延遲規格 —— SLA 才是。

### 那個部分互動性的陷阱

有些功能看起來像互動式，但忍得住 5-10 分鐘。例子：一份夜間客戶健康報告，上面有個「重新整理」按鈕。使用者按下重新整理；等 10 分鐘完全沒問題。團隊卻把它做成同步。50 個併發的重新整理，成本是「批次跑完再用電子郵件寄出」的 10 倍。

該問的問題是：「對這個使用者來說，24 小時代表什麼？」若答案是「他們根本不會注意到」，那就批次。

### 那個輸出 schema 的陷阱

各供應商的批次檔案格式不同：

- OpenAI：JSONL，一行一個請求。
- Anthropic：JSONL，一行一則訊息；回應格式內嵌其中。
- Vertex：BigQuery 表格，或帶 TFRecord 的 GCS 前綴。

要寫「一個跨供應商的批次客戶端」，就意味著每家供應商都要有轉接程式碼。那些宣傳支援多供應商批次的閘道（Portkey、LiteLLM 的某些層級）也只是把原始格式薄薄包一層。

### 你該記住的數字

- 各供應商的批次折扣：輸入 + 輸出一律五折。
- 周轉 SLA：保證 24 小時，典型 P50 為 2-6 小時。
- 疊起來的批次 + 快取輸入：同步未快取成本的約 10%。
- 工作負載檢傷規則：若 24 小時延遲可接受，永遠用批次。

## 練習

1. 跑 `code/main.py`。對一條 10 萬份文件、3K 詞元系統提示詞、500 詞元輸出的管線，算出整套堆疊（批次 + 快取）相對同步基線的節省。
2. 從你熟悉的一項真實產品中挑三個功能。把每一個檢傷分類成互動式／半互動式／批次。
3. 一位使用者抱怨他的報告花了 3 小時。那是一次批次的錯誤檢傷，還是一項正當的互動式需求？把判準寫出來。
4. 你的批次 API 回傳 SLA 是 24 小時，但 P99 是 20 小時。你要怎麼向使用者溝通這件事 —— 下游系統在那個邊界情況下的行為是什麼？
5. 算出損益平衡：共享前綴要多長，批次 + 快取才會比在你自己的保留 GPU 上隔夜跑更便宜？

## 關鍵術語

| 術語 | 大家怎麼說 | 實際是什麼意思 |
|------|----------------|------------------------|
| 批次 API | 「非同步折扣」 | 打五折，24 小時周轉 |
| JSONL | 「批次格式」 | 一行一個 JSON 請求；OpenAI／Anthropic 的標準 |
| Message Batches | 「Anthropic 的批次」 | Anthropic 批次 API 的產品名稱 |
| Batch prediction | 「Vertex 的批次」 | Vertex AI 的批次 API 產品 |
| 周轉 SLA | 「24 小時承諾」 | 是保證，不是典型值；典型是 2-6 小時 |
| 工作負載檢傷 | 「互動性的決策」 | 互動式／半互動式／批次的路由決策 |
| 輸出 schema | 「回應格式」 | 各供應商的 JSONL 版面；不可攜 |
| 疊加折扣 | 「批次 + 快取」 | 兩者都套用時是未快取同步帳單的約 10% |
