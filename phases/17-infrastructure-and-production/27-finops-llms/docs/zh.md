# 給 LLM 用的 FinOps —— 單位經濟與多租戶歸屬

> 傳統 FinOps 在 LLM 支出上會壞掉。成本是詞元交易，不是資源運轉時間。標籤對不上 —— 一次 API 呼叫是一筆交易，不是一項資產。工程決定（提示詞設計、脈絡窗口、輸出長度）就是財務決定。2026 年的操作手冊有三個歸屬維度，第一天就要插好檢測：逐使用者（`user_id`）用於席次定價與擴充；逐任務（`task_id` + `route`）用於產品介面成本與優先順序；逐租戶（`tenant_id`）用於單位經濟與續約。四個詞元層 —— 提示詞、工具、記憶、回應 —— 全部塞進一個桶子就會把支出藏起來。多租戶產品的強制執行階梯：逐租戶速率限制（預期尖峰的 2-3 倍，回傳清楚的 429 + retry-after）；每日支出上限（合約上限的 1.5-3 倍；觸發時收緊速率並發警報）；支出 z 分數 > 4 時的緊急停止開關（自動暫停 + 呼叫待命）。歸屬模式：打標籤再彙總、遙測接合（軌跡 ID → 計費；準確度最高）、抽樣再外推、以模型為基礎的分配、事件溯源、即時串流。單位指標：每次解決查詢的成本、每件產出物的成本 —— 不是每百萬詞元多少錢。回溯打標籤永遠會漏；在請求建立時就插好檢測。

**類型：** 學習
**程式語言：** Python (stdlib, toy cost-attribution simulator with kill switch)
**先修單元：** 階段 17 · 13（可觀測性）、階段 17 · 14（快取）
**時間：** 約 60 分鐘

## 學習目標

- 解釋為何傳統 FinOps（標籤 + 分層）在 LLM 支出上會壞掉，並說出那三個新的歸屬維度。
- 列舉那四個詞元層（提示詞、工具、記憶、回應），以及單桶計費為何會把成本藏起來。
- 替一個多租戶產品設計一道強制執行階梯（速率 → 支出上限 → 緊急停止開關）。
- 挑一個單位指標（每次解決查詢／每件產出物的成本），而不是每百萬詞元多少錢。

## 問題所在

你的帳單寫著 40,000 美元。你不知道：
- 是哪個租戶花掉的。
- 是哪個產品功能帶動的。
- 有沒有哪個使用者在濫用。
- 元凶是提示詞膨脹、工具呼叫，還是記憶放大。

在供應商端「打標籤再彙總」對雲端資源（EC2、S3）行得通，因為那些標籤會傳播到帳單明細上。LLM API 呼叫不會自動打標籤 —— 你得在呼叫點蓋上 user/task/tenant 並一路帶下去。回溯歸屬永遠會漏掉邊界情況。

## 核心概念

### 三個歸屬維度

**逐使用者**（`user_id`）：誰花了多少。驅動席次定價、擴充洽談，也點出重度使用者。

**逐任務**（`task_id` + `route`）：哪個產品介面花多少。驅動功能排序，以及「砍掉貴功能」的決定。

**逐租戶**（`tenant_id`）：哪個客戶賺錢。驅動單位經濟、續約定價與分層門檻。

第一天就在呼叫點把三者都插好檢測。回溯永遠比較糟。

### 四個詞元層

| 層 | 例子 | 佔總量的典型比例 |
|-------|---------|---------------------|
| 提示詞 | 系統 + 使用者輸入 | 40-60% |
| 工具 | 餵回去的工具呼叫結果 | 20-40%（代理型工作負載） |
| 記憶 | 先前對話／檢索到的文件 | 10-30% |
| 回應 | 模型輸出 | 10-30% |

把這四層混在同一個桶子裡，會讓最佳化變成瞎子摸象。在你的歸屬結構裡把它們拆開。

### 強制執行階梯

1. **速率限制**，逐租戶。預期尖峰的 2-3 倍。回傳帶 `Retry-After` 的 429。租戶感覺得到摩擦；不會有帳單驚喜。

2. **每日支出上限**，逐租戶。合約上限的 1.5-3 倍。觸發時：收緊速率限制 + 通知客戶成功團隊。

3. **緊急停止開關**，當支出相對該租戶基線的 z 分數 > 4 時。自動暫停該租戶；呼叫待命；升級給維運 + 客戶成功。

### 歸屬模式

- **打標籤再彙總**：蓋上中繼資料標頭；之後再彙總。簡單；粗糙。
- **遙測接合**：透過軌跡 ID 把軌跡接到計費上。準確度最高。成熟團隊都這樣做。
- **抽樣 + 外推**：抽樣 5-10%，再乘上去。要抓概略支出很划算；會漏掉尾端。
- **以模型為基礎的分配**：用迴歸推論成本驅動因子。適用於沒有標籤的歷史資料。
- **事件溯源**：把成本當成串流裡的事件（Kafka / Kinesis）。即時。
- **即時串流**：儀表板以次秒級更新。

### 「每 X 成本」才是單位指標

「每百萬詞元多少錢」是廠商用語。產品指標：

- 每張已解決客服工單的成本。
- 每篇產出文章的成本。
- 每項成功的代理任務的成本。
- 每分鐘使用者工作階段的成本。

把成本綁到產品成果上。否則最佳化就沒有錨點。

### 成本歸屬的軌跡形狀

```
trace_id: abc123
  user_id: u_42
  tenant_id: t_7
  task_id: task_classify_doc
  route: model_haiku
  layers:
    prompt_tokens: 1800
    tool_tokens: 600
    memory_tokens: 400
    response_tokens: 150
  cost_usd: 0.0135
  cached_input: true
  batch: false
```

每次呼叫都發出來。存進資料湖。逐維度彙總。這東西住的地方就是階段 17 · 13 的可觀測性堆疊。

### 疊加節省的堆疊

堆疊：快取 + 批次 + 路由 + 閘道。四樣全上：
- L2 快取（階段 17 · 14）：輸入便宜約 10 倍。
- 批次（階段 17 · 15）：打五折。
- 路由到便宜模型（階段 17 · 16）：降低 60% 成本。
- 閘道效率（階段 17 · 19）：冗餘 + 重試。

疊起來的最佳情況：約為天真基線的 5-10%。多數團隊只拉了 2-3 根槓桿；很少人四樣全疊。

### 你該記住的數字

- 歸屬維度：逐使用者、逐任務、逐租戶。
- 四個詞元層：提示詞、工具、記憶、回應。
- 緊急停止開關：支出 z 分數 > 4。
- 單位指標：每次解決查詢的成本，不是每百萬詞元多少錢。
- 疊加最佳化：有機會做到基線的約 5-10%。

## 練習

1. 跑 `code/main.py`。緊急停止開關在什麼 z 分數觸發？你要怎麼挑那個門檻？
2. 設計一份逐租戶、逐任務的成本儀表板。你最先做的 5 個視圖是什麼？
3. 你最大的租戶在單位經濟上是負的。提出三項介入手段，依對客戶的衝擊排序。
4. 替一個客服產品算出每張已解決工單的成本：每張工單 300 萬詞元、每天約 800 張、用 GPT-5 的快取費率。
5. 論證回溯打標籤有沒有可能行得通。什麼時候它是可以接受的？

## 關鍵術語

| 術語 | 大家怎麼說 | 實際是什麼意思 |
|------|----------------|------------------------|
| 逐使用者歸屬 | 「使用者層級成本」 | 每次呼叫都蓋上 `user_id` |
| 逐任務歸屬 | 「功能成本」 | 用 `task_id` + `route` 標出產品介面 |
| 逐租戶歸屬 | 「客戶成本」 | `tenant_id`；驅動單位經濟 |
| 四個詞元層 | 「成本分層」 | 提示詞 + 工具 + 記憶 + 回應 |
| 速率限制 | 「429 防護」 | 在閘道上執行的逐租戶上限 |
| 每日支出上限 | 「每日天花板」 | 帶警報、以租戶為範圍的預算 |
| 緊急停止開關 | 「自動暫停」 | 支出 z 分數 > 4 觸發自動停權 |
| 每次解決成本 | 「產品單位指標」 | 綁在產品成果上的成本，不是詞元 |
| 遙測接合 | 「軌跡接計費」 | 準確度最高的歸屬模式 |
| 疊加最佳化 | 「快取+批次+路由+閘道」 | 複利式節省到基線的約 5-10% |
