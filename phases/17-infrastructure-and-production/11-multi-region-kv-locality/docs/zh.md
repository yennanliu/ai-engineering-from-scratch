# 多區域 LLM 服務與 KV 快取局部性

> 對有快取的 LLM 推論而言，輪詢式負載平衡是主動有害的。一個沒落在「持有它前綴」那個節點上的請求，要付出完整的預填成本 —— 在長提示詞上 P50 大約 800 毫秒，而命中快取只要約 80 毫秒。2026 年的生產模式是一個知快取的路由器（用 Rust 寫的 vLLM Router、llm-d 的 router），它消費 KV 快取事件，並依前綴雜湊比對來路由。近期研究（GORGO）把跨區域網路延遲當成路由目標函數中的一個明確項。商用的「跨區域推論」產品（Bedrock 的 cross-region inference、GKE 的多叢集閘道）把推論當成不透明的東西 —— 它們處理的是可用性，不是 TTFT。JPMorgan 與 Mayo Clinic 在 2024 年 11 月做過 us-east-1 的故障轉移，約 22 分鐘完成。災難復原的現實是：32% 的 LLM 災難復原失敗，是因為團隊備份了權重，卻忘了分詞器檔案或量化設定。

**類型：** 學習
**程式語言：** Python (stdlib, toy prefix-cache-aware router simulator)
**先修單元：** 階段 17 · 04（vLLM 服務）、階段 17 · 06（SGLang RadixAttention）
**時間：** 約 60 分鐘

## 學習目標

- 解釋為何輪詢式負載平衡會弄壞有快取的推論，並把那個 TTFT 代價量化。
- 畫出一個知快取的路由器：輸入（KV 快取事件）、演算法（前綴雜湊比對）、決勝條件（GPU 使用率）。
- 說出 LLM 那 32% 的災難復原失敗主因（缺少分詞器檔案／量化設定），並提出一份三檔的災難復原檢查清單。
- 分辨商用的跨區域產品（Bedrock CRI、GKE Multi-Cluster Gateway）與知 KV 的路由。

## 問題所在

你的服務跑在 us-east-1、us-west-2 與 eu-west-1。你在前面擺了一個做輪詢的 ALB。生產環境的前綴快取命中率掉到 8%。TTFT P50 變成三倍。你的 vLLM 日誌顯示每個請求都在付完整的預填成本。

輪詢對無狀態服務是最佳的。LLM 推論在設計上就是有狀態的 —— KV 快取編碼了模型看過的一切。盲目路由，就是把請求路由進錯的快取。

另外，你的團隊有一份災難復原計畫。你把模型權重跨區域備份到 S3。一次區域性停擺打來；你嘗試故障轉移；那個副本拒絕啟動。你忘了 tokenizer.json、量化設定與 RoPE 縮放設定在另一個你沒同步的儲存桶裡。

多區域 LLM 服務是一個快取問題、一個路由問題，以及一個災難復原衛生問題 —— 不是一個負載平衡器問題。

## 核心概念

### 知快取的路由

請求帶著提示詞抵達。路由器對前綴（比如前 512 個詞元）做雜湊；它問每個副本「你有沒有快取這個前綴？」。副本在配置與逐出區塊時，會在一個發布／訂閱通道上發布 KV 快取事件。路由器挑出有相符的那個副本；若沒人有，就退回到以 GPU 使用率決勝。

**vLLM Router**（Rust，2026 年的 production-stack）：訂閱 `kv.cache.block_added` 事件、維護一份「前綴雜湊 → 副本」的索引，以 O(1) 查找做路由。沒有相符時退回到最短佇列深度。

**llm-d router**：同樣的模式，Kubernetes 原生。透過 ControlPlane API 發布事件。

**SGLang 的 RadixAttention**（階段 17 · 06）是副本「內部」的對應物。跨副本的路由嚴格位於它的上游。

### 數字

在 2K 詞元提示詞、Llama 3.3 70B FP8、H100 上的 TTFT P50：
- 快取命中（同一個副本、前綴常駐）：約 80 毫秒。
- 快取未命中（冷預填）：約 800 毫秒。

10 倍落差。若你的路由器在各副本間打到 60-80% 的前綴快取，你就能在 N 個副本的容量下逼近單副本的效能。若只打到 10%，那你就只是在做天真的擴展。

### 跨區域多了一項新限制 —— 網路延遲

跨區域來回時間：
- us-east-1 ↔ us-west-2：約 65 毫秒。
- us-east-1 ↔ eu-west-1：約 75 毫秒。
- us-east-1 ↔ ap-southeast-1：約 220 毫秒。

若路由把一個來自 us-east-1 的請求送去 ap-southeast-1 找熱門前綴，省下的預填（800 → 80 毫秒）會被 440 毫秒的來回吞掉。GORGO（2026 年的研究）把這件事明寫出來 —— 要聯合最小化 `prefill_time + network_latency`，不是只看預填。答案往往是把路由留在區域內，除非遇到那種預填會主導的巨大多 MB 前綴。

### 商用的「跨區域推論」在這件事上幫不上忙

AWS Bedrock 的跨區域推論會在容量吃緊時自動把請求路由到其他區域。它最佳化的是可用性、不是 TTFT，而且把推論當成不透明的東西。GKE 的 Multi-Cluster Gateway 也一樣 —— 服務層級的故障轉移，對 KV 快取毫無感知。

就算你在用這些，你仍然需要一個應用層、知快取的路由器。它們處理的是「us-east-1 起火了」那種情況。知快取的路由處理的是 TTFT 那種情況。

### 災難復原衛生 —— 那個 32% 缺檔問題

2026 年被廣泛引用的統計：32% 的 LLM 災難復原失敗，是因為團隊備份了權重，卻忘了：

- `tokenizer.json` 或 `tokenizer.model`
- 量化設定（`quantize_config.json`、AWQ 縮放值、GPTQ 零點）
- 模型專屬設定（RoPE 縮放、注意力遮罩、聊天樣板）
- 引擎設定（`vllm_config.yaml`、取樣預設值、LoRA 轉接器清單）

修法是一份最少三檔的災難復原清單：

1. HF 模型儲存庫底下的所有檔案（權重 + 設定 + 分詞器）。
2. 引擎專屬的服務設定。
3. 部署清單（K8s YAML、Dockerfile、相依鎖定檔）。

外加：每季做一次災難復原演練。JPMorgan 那次 us-east-1 演練之所以在 2024 年 11 月打到 22 分鐘復原，正是因為那份劇本被排練過。

### 資料落地是正交的

歐盟客戶的 PHI 不能離開歐盟。若你那個知快取的路由器，為了前綴相符把一個從巴黎發起的請求送到 us-east-1，那不管 TTFT 賺了多少，你都違反了 GDPR。在替快取最佳化之前，先依落地邊界把路由器分割開來。

### 你該記住的數字

- 快取命中與未命中的 TTFT 落差：約 10 倍（2K 提示詞上 80 毫秒對 800 毫秒）。
- 美歐之間的跨區域來回：約 75 毫秒。
- 災難復原失敗：32% 漏掉分詞器／量化設定。
- JPMorgan 2024 年 11 月的 us-east-1 故障轉移：22 分鐘（SLA 為 30 分鐘）。

## 關鍵術語

| 術語 | 大家怎麼說 | 實際是什麼意思 |
|------|----------------|------------------------|
| 知快取的路由 | 「聰明的負載平衡」 | 依前綴雜湊比對，路由到持有 KV 快取的副本 |
| KV 快取事件 | 「快取的發布訂閱」 | 副本發布區塊的新增／逐出；路由器建索引 |
| 前綴雜湊 | 「快取鍵」 | 前 N 個詞元的雜湊，供路由器查找 |
| GORGO | 「跨區域路由的研究」 | arXiv 2602.11688；把網路延遲當成明確的項 |
| 跨區域推論 | 「Bedrock CRI」 | AWS 的產品；可用性故障轉移，不感知 TTFT |
| 災難復原清單 | 「那份備份清單」 | 還原所需的每一個檔案 —— 不只是權重 |
| 資料落地 | 「GDPR 邊界」 | 對「哪個區域看得到使用者資料」的法律限制 |
| RTT | 「來回時間」 | 網路延遲；美歐 75 毫秒、美亞太 220 毫秒 |
| 知 LLM 的負載平衡 | 「以快取命中為目標的負載平衡」 | 把知快取路由器當成一個產品類別 |
