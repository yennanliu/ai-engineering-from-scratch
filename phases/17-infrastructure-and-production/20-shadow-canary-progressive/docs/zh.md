# LLM 的影子流量、金絲雀發布與漸進式部署

> LLM 的發布把軟體部署裡最難的幾件事湊在一起：沒有單元測試、失敗模式擴散、訊號延遲。順序是：(1) 影子模式 —— 把生產請求複製一份給候選模型，記錄下來、做比較，對使用者零衝擊；抓得到明顯的分布問題，但不是品質保證；(2) 金絲雀發布 —— 漸進地把流量從 10% → 25% → 50% → 75% → 100% 挪過去，每一步都設閘門；追蹤延遲百分位、每請求成本、錯誤／拒答率、輸出長度分布、使用者回饋率；(3) 確認穩定之後，再對明確不同的替代方案做 A/B 測試。非決定性是砍不掉的 —— 因為 GPU 浮點不具結合律，再加上批次大小的變異，同樣的輸入在不同次執行間最高會有 15% 的準確率變化。成本是變數，不是常數 —— 一個好 20% 的模型，每次呼叫可能貴 3 倍。回滾速度是決定性的：若回滾需要重新部署，你就太慢了。政策放在設定／旗標裡；模型放在登錄庫裡並釘住摘要值；回滾 = 翻政策 + 還原門檻 + 釘回舊模型，幾秒鐘的事。

**類型：** 學習
**程式語言：** Python (stdlib, toy canary-progression simulator)
**先修單元：** 階段 17 · 13（可觀測性）、階段 17 · 21（A/B 測試）
**時間：** 約 60 分鐘

## 學習目標

- 分辨影子模式（零衝擊比較）、金絲雀（實流量漸進）與 A/B（確認穩定後的比較）。
- 列舉五項 LLM 專屬的金絲雀指標（延遲、每請求成本、錯誤／拒答、輸出長度分布、使用者回饋）。
- 解釋 LLM 的非決定性（最高 15%）如何改變一次發布中「穩定」的定義。
- 設計一條只要幾秒（翻政策）而不是幾小時（重新部署）的回滾路徑。

## 問題所在

你出貨了一個新模型。離線評測顯示準確率增加 3%。你在生產環境把它打開。24 小時內，成本上升 40%、使用者倒讚上升 8%、三張客戶工單回報「答案很怪」。你回滾。重新部署要 3 小時。你的週末毀了。

這裡每一件事都是可以避免的。影子模式會在任何使用者看到之前就抓到那 40% 的成本暴衝。金絲雀會在倒讚一動的時候就停在 10%。政策旗標式的回滾只要 30 秒。這套紀律，填的就是「離線評測看起來不錯」與「真實使用者很開心」之間那道縫。

## 核心概念

### 影子模式

候選模型收到跟生產一樣的請求；輸出被記錄下來，不回傳給使用者。對使用者零衝擊。記錄：

- 輸出內容（與生產做差異比對）。
- 詞元數（成本差）。
- 延遲。
- 拒答與錯誤。

抓得到：成本爆炸、長度退化、明顯的拒答變化、硬性錯誤。抓「不到」：使用者會感受到的品質差異。影子是冒煙測試，不是品質測試。

### 金絲雀發布

帶閘門的漸進式流量轉移。典型推進：1% → 10% → 25% → 50% → 75% → 100%。每一步對 5 項指標設閘門：

1. **延遲百分位** —— P50、P95、P99。違規：金絲雀的 P99 > 基線的 1.5 倍。
2. **每請求成本** —— 混合金額。違規：高於基線 20% 以上。
3. **錯誤／拒答率** —— 5xx 加上明確的拒答。違規：基線的 2 倍。
4. **輸出長度分布** —— 平均值 + P99。違規：分布位移。
5. **使用者回饋率** —— 倒讚／開單數。違規：基線的 1.5 倍。

### 非決定性是新的變異來源

同樣的輸入產生不一樣的輸出。原因：

- GPU 浮點不具結合律（浮點歸約順序會隨批次而異）。
- 批次大小的變異（同一段提示詞在 128 的批次裡對比在 16 的批次裡）。
- 取樣（temperature > 0）。

量測結果：在同一份評測集上，不同次執行間最高有 15% 的準確率變化。一次發布中的「穩定」，指的是指標落在預期變異之內，不是跟基線一模一樣。閘門要設在噪音底線之上。

### 成本是變數

一個好 20% 的模型，每次呼叫可能貴 3 倍。每請求成本是那五道閘門之一。出貨一個「更好」卻打壞單位經濟的模型，就是一個回滾案例。

### 回滾才是你的武器

- 政策旗標（功能旗標系統）：在設定裡翻百分比；幾秒鐘。
- 模型釘選（登錄庫摘要值）：被釘住的模型不會自動升級。
- 回滾 = 還原旗標 + 把釘選摘要值設回前一版。幾秒，不是幾小時。

若你的堆疊回滾時得重新部署，那就在推出去之前先把這件事修好。

### 工具

**Argo Rollouts** / **Flagger** —— Kubernetes 的漸進式交付控制器。與 Istio/Linkerd 的加權路由整合。

**Istio 加權路由** —— 服務網格層級的流量切分。

**KServe / Seldon Core** —— 內建金絲雀的模型服務。

**功能旗標** —— LaunchDarkly、Flagsmith、Unleash。政策層級的翻轉，不必重新部署。

### 指標節奏

金絲雀閘門依流量量體，每 5-15 分鐘檢查一次。1% 流量、每分鐘 10 個請求，每個窗口能給你 50-150 個資料點 —— 對延遲夠用，但對使用者回饋太吵。10% 就多約 10 倍。推進在每一步都該暫停夠久，以累積足夠樣本。

### A/B 那一步是選配

若新模型明顯不同（行為不同、成本曲線不同、語氣不同），就在金絲雀通過後於 50% 做 A/B 測試。若它只是改良版，金絲雀閘門一過就直接推到 100%。

### 你該記住的數字

- 金絲雀推進：1% → 10% → 25% → 50% → 75% → 100%。
- 非決定性上限：同樣輸入下，不同次執行間最高 15% 的變異。
- 五項金絲雀指標：延遲、成本、錯誤／拒答、輸出長度、使用者回饋。
- 成本閘門：高於基線 20% 以上算違規。
- 回滾：幾秒，不是幾小時。

## 練習

1. 跑 `code/main.py`。注入 25% 的成本退化。金絲雀停在哪一階段？
2. 你的新模型離線準確率增加 3%，但每請求成本 +18%。這出得了貨嗎？看政策而定 —— 兩條路徑都寫一遍。
3. 設計一次端到端 60 秒以內的回滾。列出所需的基礎設施。
4. 非決定性在你的評測上顯示 ±7%。把金絲雀閘門設到不會誤報。你要用什麼倍數？
5. 影子模式在金絲雀之前抓到 40% 的成本暴衝。把那條在影子階段觸發的警報規則寫出來。

## 關鍵術語

| 術語 | 大家怎麼說 | 實際是什麼意思 |
|------|----------------|------------------------|
| 影子模式 | 「複製一份給新的」 | 零衝擊地送給候選模型以供記錄 |
| 金絲雀 | 「漸進式流量」 | 帶閘門、逐步暴露給使用者的發布 |
| 閘門 | 「發布檢查」 | 會擋住推進的指標門檻 |
| 非決定性 | 「LLM 的變異」 | 砍不掉的執行間差異 |
| 政策旗標 | 「翻旗標回滾」 | 設定層級的回滾，幾秒而不是幾小時 |
| 模型釘選 | 「登錄庫摘要值」 | 指向某個模型版本的不可變參照 |
| Argo Rollouts | 「K8s 漸進式」 | Kubernetes 原生的金絲雀／回滾控制器 |
| KServe | 「推論版 K8s」 | 帶金絲雀原語的模型服務 |
| Istio 加權 | 「網格切分」 | 服務網格的流量分流器 |
