# 提示詞快取與語意快取的經濟學

> **定價快照日期為 2026-04。** 下面的數字反映的是本課發布當下擷取的廠商費率表；在往下游引用之前，請對照所附連結的文件查證。

> 快取發生在兩層。L2（供應商層級）的提示詞／前綴快取會替重複的前綴重用注意力 KV —— Anthropic 的提示詞快取文件宣傳在長提示詞上最多降低 90% 成本與 85% 延遲；以 Claude 3.5 Sonnet 而言，快取讀取是每百萬 0.30 美元，對比全新輸入的每百萬 3.00 美元，TTL 為 5 分鐘，而 1 小時 TTL 選項的寫入要 2 倍溢價（docs.anthropic.com，2026-04）。OpenAI 的提示詞快取對 ≥1024 詞元的提示詞自動套用，並把快取輸入定在相對全新輸入約打一折（platform.openai.com，2026-04）；每個模型確切的快取費率取決於當下的費率表。L1（應用層級）的語意快取則在嵌入相似度命中時，整個跳過 LLM。廠商的「95% 準確率」指的是比對正確性，不是命中率 —— 回報的生產命中率從 10%（開放式聊天）到 70%（結構化常見問答）都有；兩家供應商都沒有公布官方基線，所以請把這些當成社群遙測，而不是保證。生產上的陷阱是：平行化會殺死快取（在第一次快取寫入完成之前就發出 N 個平行請求，可能讓花費膨脹好幾倍），而前綴裡的動態內容會讓快取完全不會命中。ProjectDiscovery 回報，把動態文字移出可快取前綴之後，命中率從 7% 變成 74%（2025-11）。

**類型：** 學習
**程式語言：** Python (stdlib, toy two-layer cache simulator)
**先修單元：** 階段 17 · 04（服務引擎內部）、階段 17 · 06（SGLang RadixAttention）
**時間：** 約 60 分鐘

## 學習目標

- 分辨 L2 的提示詞／前綴快取（在供應商端重用 KV）與 L1 的語意快取（對相似提示詞直接跳過 LLM）。
- 解釋 Anthropic 的 `cache_control` 明確標記，以及那兩種 TTL 選項（5 分鐘對 1 小時）與各自的價格倍數。
- 在給定命中率、提示詞／回應組合與詞元價格之下，算出預期的每月節省。
- 說出那個會讓帳單膨脹 5-10 倍的平行化反模式，以及那個會讓命中率塌掉的動態內容反模式。

## 問題所在

你替 RAG 服務加上提示詞快取。帳單毫無變化。你去量命中率；只有 7%。你的提示詞看起來是靜態的，但其實不是：系統提示詞裡含有精確到分鐘的當前時間、一個請求 ID，以及為了多樣性而隨機重排的範例。每個請求都寫入一筆新的快取，讀取為零。

另外，你的代理每個使用者問題會跑十次平行的工具呼叫。十個在第一次快取寫入完成之前就抵達供應商。十次寫入、零次讀取。你的帳單是「有快取」原本該有的 5-10 倍。

快取是一套協定，不是一個旗標。兩層，兩種不同的失敗模式。

## 核心概念

### L2 —— 供應商的提示詞／前綴快取

供應商把可快取前綴的注意力 KV 存起來，並在下一個前綴相符的請求上重用它。你付一次寫入成本，讀取幾乎免費。

**Anthropic（Claude 3.5／3.7／4 系列）**：在請求中放一個明確的 `cache_control` 標記。你標出哪些區塊可以被快取。TTL：5 分鐘（寫入成本為基礎的 1.25 倍）或 1 小時（寫入成本為 2 倍）。快取讀取：Claude 3.5 Sonnet 上每百萬 0.30 美元，對比全新的每百萬 3.00 美元 —— 便宜 10 倍（docs.anthropic.com，截至 2026-04）。各模型費率不同（Opus／Haiku 另外公布）；永遠去對照當下的定價頁。

**OpenAI**：對 ≥1024 詞元的提示詞自動快取（platform.openai.com，2026-04）。沒有明確的旗標。在當前的 gpt-4o/gpt-5 費率表上，快取輸入大約比全新輸入便宜 10 倍。文件與發行說明都沒有公布官方的命中率基線；社群回報大致落在 30–60%，前提是提示詞設計得夠仔細。監控 `usage.cached_tokens` 來量你自己的。

**Google（Gemini）**：透過明確的 API 做脈絡快取；100 萬詞元的脈絡讓快取更加划算。

**自架（vLLM、SGLang）**：階段 17 · 06 涵蓋 RadixAttention —— 同樣的模式，跑在你自己的運算上。

### L1 —— 應用層級的語意快取

在完全不呼叫 LLM 之前，先把提示詞雜湊、嵌入，然後找一個相似的已快取請求（餘弦相似度高於門檻，通常 0.95 以上）。命中就回傳快取的回應。未命中就呼叫 LLM 並把結果快取起來。

開源：Redis Vector Similarity、GPTCache、Qdrant。商業：Portkey Cache、Helicone Cache。

廠商的準確率宣稱，指的是「回傳的快取回應在語意上有多常是合適的」—— 不是你有多常命中。生產命中率：

- 開放式聊天：10-15%。
- 結構化常見問答／客服：40-70%。
- 程式碼問題：20-30%（細微變體會殺掉命中）。
- 重複提示詞的語音代理：50-80%（語音正規化後是固定集合）。

### 那個平行化反模式

你的代理平行發出 10 次工具呼叫。10 個都帶同一段 4K 詞元的系統提示詞。Anthropic 的快取寫入是逐請求的；第一次快取寫入大約在供應商看到提示詞後 300 毫秒完成。請求 2-10 在同一毫秒窗內抵達，每一個都遇到快取未命中。你付了 10 次寫入溢價、0 次讀取折扣。

修法：批次時先跑第一個 —— 先單獨發出請求 1，等 1 的快取填好之後再發 2-10。這替第一次工具呼叫多加 300 毫秒；替帳單省下 5-10 倍。

### 那個動態內容反模式

你的系統提示詞長這樣：

```
You are a helpful assistant. The current time is 14:32:17.
User ID: abc123. Today is Tuesday...
```

每個請求都是獨一無二的。每個請求都在寫入。零次命中。

修法：把真正靜態的東西全部移到可快取的前綴；動態內容附在快取邊界之後：

```
[cacheable]
You are a helpful assistant. [rules, examples, instructions]
[/cacheable]
[dynamic, not cached]
Current time: 14:32:17. User: abc123.
```

ProjectDiscovery 就是這樣把快取命中率從 7% 拉到 74%，並把解剖過程公布出來。

### 替隔夜工作負載把批次與快取疊起來

批次 API（階段 17 · 15）以 24 小時周轉換 50% 折扣。再疊上快取輸入，就在那之上再拿到約 10 倍。隔夜的分類、標註與報告生成工作負載，靠疊加可以降到同步未快取成本的約 10%。

### 你該記住的數字

定價點擷取自 2026-04 所附連結的廠商文件，每隔幾個月就會漂移 —— 依賴它們之前先重新確認。

- Anthropic 的快取讀取：Claude 3.5 Sonnet 上每百萬 0.30 美元，大約比全新輸入便宜 10 倍（docs.anthropic.com）。
- Anthropic 的快取寫入溢價：1.25 倍（5 分鐘 TTL）或 2 倍（1 小時 TTL）。
- OpenAI 自動快取：套用於 ≥1024 詞元的提示詞；在當前費率表上，快取輸入定價約為全新輸入的 10%（platform.openai.com）。
- 語意快取命中率（社群回報）：開放聊天約 10%；結構化常見問答最高約 70%。不是廠商文件記載的基線。
- ProjectDiscovery：把動態內容移出前綴後，命中率 7% → 74%（專案部落格，2025-11）。
- 平行化反模式：當 N 個平行請求都錯過第一次快取寫入時，典型回報是帳單膨脹 5–10 倍。

## 練習

1. 跑 `code/main.py`。切換那個平行化旗標。帳單變了多少？
2. 你的系統提示詞裡有日期。把它移出去。把前後的命中率數學算給我看。
3. 依你的請求抵達速率，算出 1 小時 TTL（2 倍寫入）與 5 分鐘 TTL（1.25 倍寫入）的損益平衡。
4. 語意快取在門檻 0.95 時命中 20%。在 0.85 時命中 50%，但你看到有錯誤的快取回應。挑出正確的門檻並論證。
5. 你每個使用者問題會批次發出 10 個平行子查詢。在不增加端到端延遲的前提下，把它改寫成對快取友善的形式。

## 關鍵術語

| 術語 | 大家怎麼說 | 實際是什麼意思 |
|------|----------------|------------------------|
| L2 提示詞快取 | 「前綴快取」 | 供應商替重複的前綴存下 KV |
| `cache_control` | 「Anthropic 的快取標記」 | 用來標出可快取區塊的明確屬性 |
| 快取寫入溢價 | 「寫入稅」 | 第一次「未命中轉快取」的額外成本（1.25 倍或 2 倍） |
| L1 語意快取 | 「嵌入快取」 | 呼叫 LLM 之前在應用層做雜湊與嵌入 |
| GPTCache | 「LLM 快取函式庫」 | 熱門的開源 L1 快取函式庫 |
| 快取命中率 | 「命中 / 總數」 | 由快取服務的請求比例 |
| 平行化反模式 | 「N 次寫入陷阱」 | N 個平行請求連續 N 次未命中快取 |
| 動態內容陷阱 | 「提示詞裡放時間的陷阱」 | 前綴中的動態位元組會殺掉命中率 |
| RadixAttention | 「副本內的快取」 | SGLang 的前綴快取實作 |
